# competitive-analysis — 競合の調査と仕分け

**競合調査の失敗はほぼ1つ。「競合にあるから作る」に着地すること。**
競合にある機能を揃えても、選ばれる理由にはならない。それは**相場**であり、無いと落ちるが、有っても勝てない。

このスキルの仕事は、調べることではなく**仕分けること**。

## 役割分界（重複させない）

| このスキルがやること | やらないこと（担当スキル） |
|---|---|
| 競合の調査と出典の記録 | コンセプト・インサイトの言語化（`strategy-insight-writer`） |
| 相場 / 差別化 / 賭け への仕分け | 要件化（`user-story-writer`） |
| 「作らない理由」の記録 | 効果の検証設計（`ux-validation-planner`） |
| 自社の位置づけの提示 | KPI への接続（`framework/kpi.md`） |
| — | 決定の記録（`ux-decision-record`） |

仕分けた結果は `strategy-insight-writer` のポジショニング（A 相場 / B 差別化 / C 賭け）と**同じ区分を使う**。二重に定義しない。

## 最初に読む

| ファイル | 何のために |
|---|---|
| `pd/products/{product-name}.md` | 自社の現在地。Past Experiments と Decisions |
| `pd/specs/01-strategy/` | 既に決めたコンセプト・ポジショニング |
| `pd/voices/` | **利用者が実際に比較検討で挙げた製品**。ここに出てこない競合は、机上の競合 |

**`voices/` に出てこない製品を「競合」と呼ばない。** 誰も比較していない相手は競合ではない。調べる前に、なぜその製品を見るのかを書く。

## 調べ方

### 1. 触れた範囲を先に決める

| 確認の度合い | 書き方 | 使ってよい範囲 |
|---|---|---|
| **実際に使った** | `実測` | 挙動・所要時間・詰まり方まで |
| **画面は見た**（デモ・動画・スクショ） | `目視` | 画面構成と表示されている情報まで |
| **資料だけ**（LP・ドキュメント・記事） | `伝聞` | 「そう書いてある」ことまで |
| **触っていない** | `未確認` | **何も書かない** |

**`未確認` の製品に評価を書かない。** 「たぶん出来ないはず」を根拠にしない。触れないなら触れないと書く。

外部資料を読んだ場合は、`SKILL.md` の「外部ソース（URL / MCP 経由）を読んだ場合」に従う — 更新日を自分で取り、古ければ古いと書く。**競合の資料は自社の資料より古びやすい。**

### 2. 機能ではなく「仕事」で並べる

機能一覧の突き合わせを作らない。**機能の有無の表は、相場を数えているだけで、何も決まらない。**

見るのは、利用者が片づけたい仕事に対して、各製品が**どういう筋で答えているか**。

```
仕事: 「先月の実績を関係者に共有する」

  自社     手で集計 → 貼り付け        3ステップ / 詰まり: 集計の粒度が毎回違う
  A社      定型レポートを自動生成      1ステップ / 粒度は固定
  B社      共有相手ごとに出し分け      2ステップ / 設定が要る
```

### 3. 仕分ける

| 区分 | 意味 | 扱い |
|---|---|---|
| **A. 相場** | ほぼ全社が持つ。無いと候補から外れる | 揃える。**差別化の根拠にしない** |
| **B. 差別化** | 一部だけが持ち、選ばれる理由になっている | 自社が取るかを決める |
| **C. 賭け** | 誰も持たない。効くかは分からない | 検証の対象。作る判断はここでしない |

判定の規則:

- **2社以上が持っていれば A（相場）。** 例外なし
- B に置くには、**それが理由で選ばれた声**（`voices/`）か、実測の差が要る。無ければ C
- 「自社に無い」ことは、それだけでは課題ではない。**A に無いものは、揃える判断をするまで課題化しない**

## 出力

```
■ 対象: <自社> vs <競合>  調査日: <日付>
■ なぜこの競合か: voices/ で <n> 件、比較検討で挙がっている

┌ 仕分け
│ A 相場   CSV 出力            自社 有 / A社 有 / B社 有     → 揃っている。以上
│ A 相場   権限の細分化         自社 無 / A社 有 / B社 有     → 未対応。揃えるか決める
│ B 差別化 共有相手ごとの出し分け  自社 無 / A社 無 / B社 有     → 根拠: voice #142「相手ごとに作り直している」
│ C 賭け   実績の自動要約        どこにも無い                → 検証対象。作る判断はしない
└

■ 確認の度合い
  A社 実測（14日間の試用）/ B社 目視（デモ動画のみ。管理画面は未確認）

■ 作らないと決めたもの
  - <機能>: A（相場）だが、voices/ に要望 0 件。<日付> に再確認する

■ 次に決めること
  - 権限の細分化を揃えるか（揃えないなら、失注時の理由として記録する）
```

## やってはいけないこと

- **「競合にあるから」を差別化（B）として記録する**（必ず A）
- 触っていない製品を評価する。`未確認` を空欄で誤魔化す
- 機能の有無の比較表を成果物にする
- 競合に有って自社に無いものを、そのまま課題・要望として登録する
- `voices/` に出てこない製品を競合として扱う
- 調査結果をそのまま `products/{product-name}.md` に反映する（外部ソース由来の反映は選択式。`SKILL.md` に従う）
- 価格の比較だけで「安い / 高い」と結論づける（何が含まれるかを揃えずに比べない）
