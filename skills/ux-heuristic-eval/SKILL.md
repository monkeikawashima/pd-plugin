# ux-heuristic-eval — 原則に照らした網羅点検

**これは「声の代わり」ではない。** ヒューリスティック評価が出すのは、原則から見た**違反の疑い**であって、利用者が実際に困った証拠ではない。声が取れるなら声が優先される。

使いどころは1つ。**まだ声が無い画面で、洗い出しの抜けを減らすこと。**

## 役割分界（重複させない）

| このスキルがやること | やらないこと（担当スキル） |
|---|---|
| 原則に沿った網羅走査 | 顧客ボイスとの突合（`ux-design-review`） |
| 違反候補への重大度づけ | 検証の実施設計（`ux-validation-planner`） |
| 直す順番の提示 | コントラストの検算（`a11y-contrast-guard`） |
| — | 操作の a11y 検査（`a11y-interaction-guard`） |
| — | 文言そのものの点検（`ux-writing-guard`） |
| — | 層の判定（`ux-layer-triage`） |
| — | 決定の記録（`ux-decision-record`） |

`ux-design-review` との違いは**入力**にある。design-review は声を引き当ててから評価する。こちらは声が無い状態で走らせる。**両方やる場合は、先にこちらで洗い、design-review で声と突き合わせる。**

## 最初に読む

| ファイル | 何のために |
|---|---|
| `pd/specs/04-skeleton/screens/` | 対象画面の仕様（あれば） |
| `pd/specs/01-strategy/glossary.md` | 呼称。用語の不統一を違反として拾うため |
| `pd/voices/` | **既に声があるなら、この スキルは使わない**（design-review へ回す） |

## 走査する原則

各項目について「違反あり / 違反なし / 判定不能」を必ず埋める。**飛ばさない。**「判定不能」は、対象が画面に無いか、確認できなかったことを表す。

| # | 原則 | 見るところ |
|---|---|---|
| 1 | 状態の可視性 | いま何が起きているか。処理中・保存済み・失敗が分かるか |
| 2 | 現実との一致 | 画面の語が利用者の語か。内部用語が漏れていないか |
| 3 | 利用者の制御と自由 | 取り消せるか。誤操作から戻れるか |
| 4 | 一貫性と標準 | 同じ操作が同じ見た目か。他画面と矛盾していないか |
| 5 | エラーの予防 | 起きてから知らせるのではなく、起こさせない作りか |
| 6 | 想起より認識 | 覚えていないと使えない箇所が無いか |
| 7 | 柔軟性と効率 | 慣れた人の近道があるか（無くてもよいが、無いことを知っておく） |
| 8 | 最小限の設計 | competing する情報が同じ強さで並んでいないか |
| 9 | エラーからの回復 | 何が起きたか・次に何をするかが書いてあるか |
| 10 | ヘルプと説明 | 詰まる箇所に、その場で読めるものがあるか |

さらに pd では次の3つを足す。**空振りは実装で最も落ちやすく、原典の10項目では拾えない。**

| # | 原則 | 見るところ |
|---|---|---|
| 11 | 空振りの設計 | 0件・結果なし・権限なしのときに沈黙していないか |
| 12 | 待ちの設計 | 遅いとき、何を待っているか分かるか。無言で固まらないか |
| 13 | 入口の存在 | その画面へ**どこから辿り着けるか**。辿り着けない画面は無いのと同じ |

## 重大度

**印象で「高・中・低」と書かない。** 3つの軸を埋めてから決める。

| 軸 | 問い |
|---|---|
| 頻度 | 何人が、どれくらいの割合で当たるか |
| 影響 | 当たったとき、作業は止まるか／遅れるだけか |
| 回避 | 利用者が自力で抜けられるか。抜け方に気づけるか |

| 重大度 | 条件 |
|---|---|
| **4 停止** | 作業が完了できない。自力で抜けられない |
| **3 重い** | 完了はできるが、詰まる。回避策に気づきにくい |
| **2 軽い** | 遅くなる・迷うが、抜けられる |
| **1 指摘** | 気づく人だけが気づく |

**頻度が分からない場合は「頻度: 未取得」と書き、重大度を1段下げない。** 分からないことを、軽いことにしない。

## 出力

```
■ 対象: <画面名>  走査日: <日付>  仕様: <参照した screens/ のファイル / 無し>
■ 声の状況: 未取得 / <n>件（あるなら ux-design-review を使う）

┌ 原則走査
│ 1 状態の可視性     違反あり   保存したか分からない（保存後に何も出ない）      重大度 3
│ 2 現実との一致     違反なし
│ ...
│ 11 空振りの設計    違反あり   検索0件で白紙になる（次の行動が無い）         重大度 4
│ 13 入口の存在      判定不能   この画面への導線を確認できなかった
└

■ 直す順番（重大度 → 直す手数）
  1. [4] 検索0件が白紙        → 空振り時の文言と次の行動を置く
  2. [3] 保存の結果が出ない    → 完了の表示を足す

■ 検証が要るもの（この評価では決まらない）
  - 「保存できたか不安」は推定。<n>人に触ってもらうまで Fact にしない
```

すべての指摘に `Interpretation` を付ける。**このスキルの出力に `Fact` は存在しない。**

## やってはいけないこと

- 声があるのにこのスキルで済ませる（`ux-design-review` へ回す）
- 走査項目を飛ばす。「該当なし」と「判定不能」を混ぜる
- 重大度を印象で決める（頻度・影響・回避を埋めてから決める）
- 指摘と一緒に実装方法まで決めてしまう（何を直すかと、どう直すかを混ぜない）
- このスキルの結果だけで `products/{product-name}.md` の Context を書き換える
- 原則の名前だけ書いて、画面のどこがそれに当たるかを書かない
