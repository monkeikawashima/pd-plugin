# ux-design-review — レビューと改善案

## 役割分界（重複させない）

| このスキルがやること | やらないこと（担当スキル） |
|---|---|
| UI の評価（層ごとの観点） | 層の判定（`ux-layer-triage`） |
| 顧客ボイスとの突合 | ボイスの記録（`user-voice-ledger`） |
| 原則チェック | コントラストの検算（`a11y-contrast-guard`） |
| 指摘の切り分け（課題 / 仮説） | 検証の実施設計（`ux-validation-planner`） |

## 手順

### 1. 顧客ボイスとの突合（**必須。飛ばさない**）

```bash
pnpm voices query --screen <画面名>
```

| ID | type | 内容 | 判定 |
|---|---|---|---|
| VOICE-xxx | pain | … | 解消した / 未解消 |
| VOICE-yyy | positive | … | **壊していない / 壊している** |

- `positive` を必ず見る（**効いているものを壊す改善**が最も見つけにくい）
- 0件 → 「**一次情報なし**」と明記し、以降の改善案に「**デザイナー起案**」と書く

### 2. 層ごとの観点チェック

| 層 | 観点 |
|---|---|
| 要件 | この画面はどのストーリーを満たすか。どの原則に効くか |
| 構造 | このフェーズのコアが主役になっているか。ハブから辿れるか |
| 骨格 | コアへ最短で導けているか。**5状態（初期・処理中・成功・空振り・エラー）が揃っているか** |
| 表層 | トークンを使っているか。検算済みか。**状態を色だけで区別していないか** |

> ⚠️ **空振り（処理は成功したが有効な結果が無い）の設計を必ず確認する。**
> 「0件」「該当なし」「AI が答えを出せなかった」の設計が抜けたまま実装される事故が最も多い。

### 3. 原則チェックリスト

`pd/specs/02-requirements/experience-principles.md` から**その場で生成する**（このファイルに原則を書かない）。
原則が未定義なら「**原則未定義のためチェック不能**」と明記する。

### 4. 指摘を切り分ける（**必須**）

| 種類 | 判定 | 扱い |
|---|---|---|
| **見れば分かる課題** | 誰が見ても同じ結論（基準違反・状態欠落・文言の誤り・トークン外の値） | **直す。議論しない** |
| **検証しないと決まらない仮説** | 前提を変えると結論が変わる（配置・優先順位・情報量） | 等価案にして `ux-validation-planner` へ |

切り分けずに全部並べると、直せるものが議論で止まり、決まらないものが独断で決まる。

### 5. 記録する

`pd/reviews/DR-YYYYMMDD-NN-<slug>.md` に残す。

## 出力形式

```
■ 対象: <画面名 / コンポーネント>
■ 突合したボイス: n 件（一次情報なしの場合はその旨）
   VOICE-xxx pain  → 解消 / 未解消
   VOICE-yyy positive → 壊していない / 壊している

■ 層ごとの指摘
   要件: …
   構造: …
   骨格: …（5状態の充足: 初期✓ 処理中✓ 成功✓ 空振り✗ エラー✓）
   表層: …

■ 切り分け
   見れば分かる課題（n 件）:
     1. <指摘> → <直し方>
   検証しないと決まらない仮説（n 件）:
     1. <論点> → 案A / 案B、計測項目: …

■ 改善案の出所
   VOICE-xxx に基づく: …
   デザイナー起案: …

■ 次のアクション: <スキル名>
■ 記録先: pd/reviews/DR-…
```

## 禁止

- ボイスを引き当てずにレビューする
- 引き当てていない改善案を「顧客の声に基づく」と書く
- 指摘を切り分けずに列挙する
- `positive` を確認せずに改善案を出す
- 空振りの設計を確認せずに「問題なし」と結論する
- コントラスト比を目分量で判定する（`a11y-contrast-guard` へ渡す）
