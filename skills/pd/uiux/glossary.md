# 用語集 — 唯一の定義

同じ言葉を別の意味で使わないための定義集。**ここに書かれた意味以外で使わない。**

プロダクト固有のオブジェクト名・画面名は**ここに書かない**（`pd/specs/03-structure/` が持つ）。

---

## 1. フレーム用語

| 用語 | 定義 |
|---|---|
| **5段階モデル** | 戦略 / 要件 / 構造 / 骨格 / 表層 の5層。UI/UX の議論を層に割り当ててから中身に入るための座標系 |
| **層** | 上記5つのいずれか。「どの層の話か」が決まるまで中身の議論に入らない |
| **SoT（Source of Truth）** | ある情報の正本。同じ情報が2箇所にあるとき、どちらが正かを1つに決めたもの |
| **更新の連鎖** | 上流の層が変わったとき、下流のどこを再検証するかを辿ること。一方向（上→下） |
| **コンセプト還元テスト** | 施策がコンセプト文のどの要素に効くかを一文で書けるかの検査。書けなければ「まだ要件ではない」 |
| **作業仮説** | 上流が未定義のまま下流を進めるために置く仮定。**棄却条件が必ず付く** |
| **棄却条件** | 何が観測されたらその仮説・仮定を捨てるか。これが無いものは仮説ではない |
| **一次情報** | 直接取得した事実（逐語・ログ・実測値）。要約・伝聞・推測は含まない |
| **空振り** | 機能が起動したが有効な結果を返せなかった状態。「エラー」とは別に必ず設計する |
| **UXDR** | UX Decision Record。決めたこと**と決めなかったこと**の記録 |

## 3. 業務用語

このプロダクトは**利用者が2系統**あり、主要タスクとその完了時間もそれぞれに定義される。
**片方の時間だけを改善して「速くなった」と言わない。**

### 3.1 利用者の呼称

| 呼称 | 定義 |
|---|---|
| **ゲスト** | 飲食店を探して予約する側の利用者。訪日旅行者・日本在住者の両方を含む |
| **店舗スタッフ** | 掲載情報と予約を運用する側の利用者 |
| **管理者** | サービス全体を運用する側 |

> 「ユーザー」という語を単独で使わない。**必ずどちらかを指定する。**

### 3.2 予約完了時間（ゲスト側の主要タスク時間）

> ゲストが「行く店を決めて予約を送信し終える」までにかかる時間。

構成要素（**分解して定義する。全体と部分を混同しない**）:

| 要素 | 定義 |
|---|---|
| 探索時間 | 検索・絞り込み・一覧の閲覧に費やす時間 |
| 検討時間 | 個別の店舗情報を読んで比較する時間 |
| 入力時間 | 予約フォームの入力から送信完了までの時間 |

`予約完了時間 = 探索時間 + 検討時間 + 入力時間`

⚠️ **入力時間だけの改善を「予約完了時間の改善」と呼ばない。**

### 3.3 予約対応時間（店舗側の主要タスク時間）

> 店舗スタッフが「入った予約リクエストに決着をつける」までにかかる時間。

| 要素 | 定義 |
|---|---|
| 確認時間 | 予約の存在に気づいてから内容を把握するまで |
| 判断時間 | 受けるか断るかを決めるまで |
| 処理時間 | 承認 / キャンセル / 審査の操作を完了するまで |

`予約対応時間 = 確認時間 + 判断時間 + 処理時間`

### 3.4 品質の4軸

時間側とは**必ず対で**扱う。時間だけの改善報告をしない。

| 軸 | 問い |
|---|---|
| 正確さ | 意図した結果に到達したか（誤操作・取り違えが無いか） |
| ダイレクトさ | 目的まで最短で辿り着けたか（迂回・往復が無いか） |
| スピード | 主要タスク時間そのもの |
| ユーザー体験 | 迷い・不安・不快が無かったか |

> 各軸の自社定義（何をどう測るか）は `pd/specs/01-strategy/kpi.md` に書く。**未取得なら「未取得」と書く。**

### 3.5 多言語に関する用語

| 用語 | 定義 |
|---|---|
| **ロケール** | 表示言語。対応は `src/i18n/routing.ts` の `routing.locales` が真実の源 |
| **読者ペルソナ** | ロケールごとに異なる想定読者。ロケール＝翻訳先ではなく、**読者が違う**（`.devin/rules/lp-copy.md`） |

> ボイス台帳でロケールを扱うときは `tags` に `locale:<code>` の形で入れる（frontmatter のキーは増やさない）。

## 4. 混同されやすい語

| ✕ 混同 | ◯ 区別 |
|---|---|
| 実装済み / 解消 | **実装済み**＝機能の有無。**解消**＝再検証で再発しないと確認した状態 |
| pain / request | **pain**＝困っている事実。**request**＝話者が出した解決手段 |
| コアに据える / 面積を最大化する | コアであることは、画面上で最大であることを意味しない |
| 確認できない / 存在しない | 調査範囲を添えない限り「無い」と書かない |
