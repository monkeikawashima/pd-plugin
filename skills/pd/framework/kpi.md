# KPI

成果指標をどう分解し、改善 Driver を見つけるかを定義する。

**このファイルに特定プロダクトの KPI を書かない。** AHT、ACW、予約数、GMV、CVR、特定商品の売上 などの固有指標は、対象プロダクトで必要になった場合に Product Context 側で扱う。ここに置くのは分解の方法だけ。

---

## KPI Driver Analysis

最終 KPI を直接見つめても、動かせる対象には辿り着かない。階層で分解する。

```
Business Outcome
  ↓
Product Outcome
  ↓
User Behavior
  ↓
UX / Workflow
  ↓
Product Capability
```

見つけたいのは、**最終 KPI に最も大きな影響を与えている Driver は何か**。

手順:

1. KPI を構成式で表す（率 × 量、または段階ごとの通過率の連鎖）
2. 構成式のどの項が動いたかを特定する
3. その項を、動きが局在するまで分割する（Cohort / チャネル / デバイス / 地域 / 利用歴 / プラン など）
4. 一段下の階層へ降りて、同じことを繰り返す

**変えられるものに到達したら止める。**

Driver の評価軸（Impact / Evidence / Confidence / Controllability）は `discovery.md` を参照する。

## KPI Tree

対象プロダクトに合わせて、その都度構築する。

```
Primary KPI
├── Driver A
│   ├── Driver A-1
│   └── Driver A-2
└── Driver B
    ├── User Behavior
    └── UX / Product Capability
```

固定のテンプレートへ当てはめない。他プロダクトで作った Tree を持ち越さない。分岐は、そのプロダクトの構成式から導く。

---

## Leading / Lagging

最終 KPI だけで効果を判断しない。遅く、雑音が多い。

```
Input → Behavior → Leading Indicator → Product Outcome → Business KPI
```

- **Leading Indicator** — 最終 KPI より先に変化する指標。介入の効果が最初に現れる場所
- **Lagging Indicator** — 結果として最後に動く指標。事業上の意味を持つが、判断には遅い

連鎖のどこが**観測されたもの**で、どこが**仮定されたもの**かを明示する。段と段の接続が仮定であるなら、それ自体が検証対象になる。

---

## 定量指標の型

対象プロダクトに応じて必要な型だけを使う。具体的な指標名は Product Context 側で定義する。

| 型 | 見るもの |
|---|---|
| Funnel | 段階ごとの通過率。どこで落ちるか |
| Conversion | 特定の行動への転換率 |
| Adoption | 対象母集団のうち、実際に使い始めた割合 |
| Frequency | 単位期間あたりの利用回数。反復しているか |
| Retention | 時間経過後にどれだけ残るか |
| Task Success | 目的の操作を完了できた割合。所要時間・エラー率と対で見る |

Task Success を伴わない Conversion、Retention を伴わない Adoption は、成果を過大評価する。時間の指標だけを改善報告に使わない。品質の指標と対で示す。

---

## 成果指標に載らない価値

Primary KPI が動かないことは、価値が無いことと同じではない。導入・継続の判断では、KPI に現れない変化も評価の対象になる。**ただし「KPI が動かなかった」の言い換えとして使わない。** それぞれ、独立して観測できる形にする。

| 型 | 見るもの | 観測の例 |
|---|---|---|
| Quality | 成果物・応対・出力の正確さ、手戻りの量 | エラー率、やり直し率、事後修正の件数 |
| Variance | ばらつき。平均が同じでも分布が締まっていれば改善 | 分位差、標準偏差、外れ値の頻度 |
| Ramp-up | 新規の習熟にかかる時間・支援量 | 一定水準に達するまでの期間、質問・エスカレーションの件数 |
| Operational Cost | 運用・教育・管理にかかる労力 | 対応工数、教育時間、属人性の度合い |
| Experience | 実施者の負荷・迷い・心理的コスト | 迷いの発生箇所、離職・定着、自己申告の負荷 |
| Risk | 失敗の重大度と発生確率 | 重大インシデント数、逸脱の検出率 |

原則:

1. **Primary KPI と同じ厳しさで扱う。** 観測方法が無いものは `Unknown` であり、価値の主張として使わない
2. **Before / After の比較対象を先に決める。** 事後に有利な指標を探して価値の根拠にしない
3. **コストと対で示す。** 導入判断は価値とコストの比較であり、価値の列挙ではない

平均が横ばいでも Variance が縮小している、Primary KPI は同じでも Quality が上がっている — このどちらも Product Value である。逆に、これらを確認せずに `NO GO` を出す判断は、根拠が不足している。

## Segment 分析

平均値だけで判断しない。可能な限り分解する。

```
利用者 / 非利用者
Heavy User / Light User
Before / After
新規 / 継続
習熟度
User Segment
Task Segment
利用頻度
Cohort
```

対象プロダクトにとって意味のある Segment だけを使う。全種類を機械的に並べない。

**Product Context 側に「必須 Segment」が定義されている場合、それを先に見る。** 分析のたびに切り口を場当たりに決めると、前回との比較ができなくなる。

注意点:

- 全体が横ばいでも、上昇している Segment と下降している Segment が打ち消し合っている場合がある
- Segment 間の差は、その Segment の属性ではなく、母集団の構成変化に由来することがある
- Before / After は、同時期に起きた他の変化を排除できない。単独では因果の証明にならない

---

## 変化が観測されないときの読み方

「横ばい」は結論ではなく、2つの状態が同じ見え方をしているだけである。切り分ける前に効果の有無を判定しない。

```
(a) 差が無い          — 介入が Driver に効いていない
(b) 差が見えていない  — 差はあるが観測に埋もれている
```

(b) の主な要因:

| 要因 | 内容 | 確認方法 |
|---|---|---|
| 検出力不足 | 対象数・期間が、想定効果量を検出するには足りない | 想定効果量と現状の分散から、必要な対象数を概算する |
| 分散が大きい | 指標そのもののばらつきが効果量を上回る | 平均ではなく分布・分位で見る |
| 希釈 | 介入が届いていない対象が母集団に含まれ、平均が薄まる | 到達層と非到達層に分けて再集計する |
| 打ち消し合い | 上昇 Segment と下降 Segment が相殺している | Segment 分解（前節） |
| 構成変化 | 対象の内訳（難易度・種別・新規比率）が期間で変わった | Before / After の母集団構成を突き合わせる |
| 計測の変更 | 定義・取得経路・除外条件が期間中に変わった | 計測実装と定義の変更履歴 |

**判定の順序**は (b) を先に潰す。(b) が残っている状態の「効果なし」は、`Fact` ではなく `Unknown` である。

必要な対象数を概算できない場合、「効果が無い」ではなく **「この規模では検出できない」** と書く。両者を同じ言葉で報告しない。

### 介入の到達で層別する

介入が全対象に等しく届いているとは限らない。届いていない前提があるなら、全体平均は定義上動かない。

```
全体            介入が配布された全対象（＝多くの場合、報告されている数値）
到達層          実際に介入を経由した対象
非到達層        経由しなかった対象
到達の分布      対象者ごとの到達率（誰が・どれだけ使ったか）
```

見るのは3点。

1. 全体と到達層で成果指標が違うか — 違えば介入自体には効果があり、律速は到達側
2. 到達率の分布が偏っていないか — 一部だけが使っている場合、全体平均は到達率で決まる
3. 到達層と非到達層で、母集団の性質が違わないか — 違うなら差は介入の効果ではなく選択の結果

**到達層の差を、そのまま介入の効果として報告しない。** 使う対象を選んでいるのは介入ではなくユーザーであり、この比較は無作為割付ではない。効果の上限を示す弱い Evidence として扱い、その性質を結果の解釈に持ち越す（`experiment.md` の「検証できない場合」を参照）。

## KPI と UX の接続

KPI の分解は、UX / Workflow の層まで降りて初めて改善対象に届く。

```
KPI が動かない
  ↓  どの構成項か
  ↓  どの Segment か
  ↓  どの User Behavior か
  ↓  どの UX 観点か（Awareness / Trigger / Learning / Usability / Trust / Value / Workflow）
  ↓
改善 Driver
```

UX 観点の定義は `discovery.md` を参照する。

最終 KPI だけで Product Value を判断しない。使われていない機能と、使われて失敗している機能は、最終 KPI の上では区別できない。
