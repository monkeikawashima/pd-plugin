# ux-screen-spec-writer — 骨格層の起草

**作る前の層。** ここが空だと、画面の良し悪しは実装されたあとにしか議論できなくなり、
`ux-design-review` が「作り直しの指摘」しか出せなくなる。

## 役割分界（重複させない）

| このスキルがやること | やらないこと（担当スキル） |
|---|---|
| 画面仕様の起草（実装前） | 層の判定（`ux-layer-triage`） |
| 5状態の設計（**空振りを含む**） | 実装済み UI の評価（`ux-design-review`） |
| 面積配分の根拠づけ・等価案の提示 | 新規オブジェクトの新設（`object-model-reviewer`） |
| 使用トークンの指定（**名前のみ**） | 色の値の決定（`design-token-keeper` / **DESIGN**） |
| — | コントラストの検算（`a11y-contrast-guard`） |
| — | 検証の実施設計（`ux-validation-planner`） |

## 最初に読む

| ファイル | 何のために |
|---|---|
| `pd/specs/03-structure/core-objects.md` | このフェーズのコアは何か |
| `pd/specs/03-structure/object-model.md` | 画面に出す対象物の名前 |
| `pd/specs/02-requirements/journeys.md` | この画面が担うステップ |
| `pd/specs/02-requirements/user-stories.md` | 対応するストーリー |
| `pd/specs/05-surface/design-system.md` | **UI を書く前の参照先**（コンポーネントの出所） |
| `pd/specs/05-surface/design-tokens.md` | 使えるトークン名 |

> ⚠️ **構造層の成果物が無いまま書き始めない。** 無い場合は作業仮説として明示し、棄却条件を付ける。

## 手順

### 1. 顧客ボイスを引き当てる（**必須。飛ばさない**）

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/voices.mjs" query --screen <画面名>
```

0件なら「**一次情報なし**」と書き、以降の設計に「**デザイナー起案**」と明記する。
`positive` のボイスは「**壊してはいけないもの**」として別に控える。

### 2. 判断基準を一文で書く

> **この画面は、いまのフェーズのコアへ最短で導けているか。**

答えられないなら、それは骨格の問題ではない。**構造層に戻る。**

### 3. 面積配分を決める（決まらなければ等価に並べる）

一意に決まらないものを1案だけ書くと、**書いた人の好みが既定値になる**。

| 案 | 配置 | 前提（この案が正しくなる条件） | 棄却条件 |
|---|---|---|---|
| A | | | |
| B | | | |

**＋「何を計測すれば決まるか」を必ず書く。** これの無い等価案は、ただの先送り。

> ⚠️ 「コアに据える」と「面積を最大化する」を混同しない。

### 4. 5つの状態をすべて埋める

| 状態 | 設計 |
|---|---|
| 初期 | |
| 処理中 | |
| 成功 | |
| **空振り**（処理は成功したが有効な結果が無い） | |
| エラー（処理そのものが失敗） | |

> ⚠️ **空振りを省略しない。** 「0件」「該当なし」「答えを出せなかった」の設計が抜けたまま
> 実装されると、利用者の前に沈黙が残る。エラーとは**別物**として必ず書く。

### 5. 表層は名前だけ指定する

| 書いてよい | 書いてはいけない |
|---|---|
| トークン名（`color.text.muted` など） | `#` から始まる色の値 |
| 「コントラスト検算 未」 | 検算結果の代わりになる感想 |

**色の値を画面仕様に直書きしない。** トークンの外側に値が増えると、テーマ変更が破綻する。
検算は `a11y-contrast-guard`、値の決定は `design-token-keeper` と DESIGN。

### 6. サンプル値に印を付ける

表示例に置いた数値・文言には**必ず「サンプル値」と明記する**。
明記が無い値は、後から実測値として引用される。

### 7. 書く

`skills/analyze/uiux/templates/screen-spec.md` を Schema として
`pd/specs/04-skeleton/screens/<画面名>.md` に書く（現在値）。

複数案が並んだままの状態は `status: 未合意`。**未合意のまま実装の根拠にしない。**
レイアウトの前提そのものが決まらない場合は `pd/specs/04-skeleton/layout-hypotheses.md` に等価案を置く。

### 8. 渡す

| 出てきたもの | 次のスキル |
|---|---|
| 等価案が残った | `ux-validation-planner` |
| 対象物が足りない | `object-model-reviewer` |
| 色・コントラスト | `a11y-contrast-guard` → `design-token-keeper` |
| 合意した / しなかった | `ux-decision-record` |
| 実装後の確認 | `ux-design-review` |

## 出力形式

```
■ 画面: <画面名>（status: 起草 / 合意済み / 未合意 / 要再検証）
■ 担うジャーニーのステップ: <ステップ名 / 未対応>
■ コアオブジェクト: <対象物名>
■ 顧客ボイス: <件数>（0件なら「一次情報なし」＋デザイナー起案）
■ 判断基準への答え: <一文 / 答えられない（構造層へ戻る）>
■ 面積配分: 一意に決まった / 等価案 A・B（計測項目: <…>）
■ 5状態: 初期 / 処理中 / 成功 / 空振り / エラー ← すべて埋めたか
■ 使用トークン: <名前のみ>（コントラスト検算: 済 / 未）
■ 記録先: pd/specs/04-skeleton/screens/<画面名>.md
```

## 禁止

- 空振り状態を設計せずに仕様を確定する
- 色の値を画面仕様に直書きする
- 決まらない配置を1案だけ書く
- サンプル値に印を付けない
- `未合意` のまま実装の根拠にする
- ボイスを引き当てずに書いた設計に「デザイナー起案」を付けない
