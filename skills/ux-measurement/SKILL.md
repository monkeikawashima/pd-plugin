# ux-measurement — 計測設計と報告

## 役割分界（重複させない）

| このスキルがやること | やらないこと（担当スキル） |
|---|---|
| 数値指標の定義とベースライン取得 | 定性検証の設計（`ux-validation-planner`） |
| 継続計測と報告 | KPI 定義変更の連鎖処理（`ux-update-cascade`） |
| 未取得指標の明示 | 定義の記録（`ux-decision-record`） |

**前提**: 公開された運用 KPI ベンチマークが存在しない領域は珍しくない。
他社比較ではなく、**自社のベースラインを計測する設計そのものが提供価値**。

## 最初に読む

`pd/specs/01-strategy/kpi.md`（時間側・品質側の定義とベースラインの有無）
`skills/pd/uiux/glossary.md` §3（主要タスク時間の定義と構成要素）

## 何を測るか

### 1. 時間側 — 主要タスクの完了時間

**必ず構成要素に分解して定義する。**

> ⚠️ **部分指標を全体指標の言い換えにしない。**
> 一部の工程だけを改善して「主要タスク時間が改善した」と報告すると、
> 改善されていない工程が成果から抜け落ちたまま固定される。

### 2. 品質側（4軸）— **時間側と必ず対で出す**

| 軸 | 問い |
|---|---|
| 正確さ | 意図した結果に到達したか |
| ダイレクトさ | 目的まで最短で辿り着けたか |
| スピード | 主要タスク時間そのもの |
| ユーザー体験 | 迷い・不安・不快が無かったか |

標準指標が無い軸は自社定義を作る。**定義が無いまま数値だけ出さない。**

### 3. 骨格の判断材料

フォーカス計測（視線・操作の集まり方）。等価案の優劣を決める材料。

### 4. ボイス側

- 未解消の `pain` / `negative` の件数（`pnpm voices stats`）
- 利用率
- **空振り率** — 処理は成功したが有効な結果を返せなかった割合。**エラー率とは別物**

---

## 手順

1. 指標を定義する（何をどこからどこまで、どう数えるか）
2. ベースラインの有無を確認する
3. **未取得なら「未取得」と明記する**（それらしい数字を置かない）
4. 計測方法とログ項目を決める
5. 取得する
6. 報告する

## 出力形式

```
■ 指標: <名前>
   定義: <何をどこからどこまで測るか>
   計測方法: <ログ / 実測 / 観察>
   ベースライン: <値（取得日）> / **未取得**
   今回値: <値> / 未取得
   差分: <値> / 算出不能（ベースライン未取得）
   解釈: <一文。一次情報から読み取れないことには [推測] を付ける>

■ 時間側と品質側の対応
   時間: … / 品質: …（片方だけの報告をしない）

■ 未取得の指標一覧
   - <指標名>（取得するには: <何が必要か>）

■ 記録先: pd/measurements/MP-YYYYMMDD-NN-<slug>.md
```

## 禁止

- ベースライン未取得のまま「改善した」と言う
- それらしい数値を置く（`約30%改善` など出所のない数字）
- 時間だけの改善報告（品質側と対で出す）
- 部分指標を全体指標の名前で呼ぶ
- 空振り率をエラー率に含める
- 業界平均・ベンチマークを、出典なしに書く
