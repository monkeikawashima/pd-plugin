# 用語集 — 唯一の定義

同じ言葉を別の意味で使わないための定義集。**ここに書かれた意味以外で使わない。**

**ここに書くのは、どのプロダクトでも同じ意味を持つ語だけ。**
利用者の呼称・オブジェクト名・画面名・業務用語といったプロダクト固有の語は書かない。
それらの定義先はプロジェクト側（`pd/specs/01-strategy/glossary.md` と `pd/specs/03-structure/`）。

固有の語をここに書くと、他のプロダクトでその言葉が間違ったまま強制される。
**§3 が「書き方だけ」なのはそのため。**

---

## 1. フレーム用語

| 用語 | 定義 |
|---|---|
| **5段階モデル** | 戦略 / 要件 / 構造 / 骨格 / 表層 の5層。UI/UX の議論を層に割り当ててから中身に入るための座標系 |
| **層** | 上記5つのいずれか。「どの層の話か」が決まるまで中身の議論に入らない |
| **SoT（Source of Truth）** | ある情報の正本。同じ情報が2箇所にあるとき、どちらが正かを1つに決めたもの |
| **更新の連鎖** | 上流の層が変わったとき、下流のどこを再検証するかを辿ること。一方向（上→下） |
| **コンセプト還元テスト** | 施策がコンセプト文のどの要素に効くかを一文で書けるかの検査。書けなければ「まだ要件ではない」 |
| **作業仮説** | 上流が未定義のまま下流を進めるために置く仮定。**棄却条件が必ず付く** |
| **棄却条件** | 何が観測されたらその仮説・仮定を捨てるか。これが無いものは仮説ではない |
| **一次情報** | 直接取得した事実（逐語・ログ・実測値）。要約・伝聞・推測は含まない |
| **空振り** | 機能が起動したが有効な結果を返せなかった状態。「エラー」とは別に必ず設計する |
| **UXDR** | UX Decision Record。決めたこと**と決めなかったこと**の記録 |

## 2. 役割の呼称

| 記号 | 呼称 | 責任 |
|---|---|---|
| BIZ | 企画 | 誰のために作るか、何を成功と呼ぶか |
| DEV | 開発 | データ構造上の実体、実装可能性 |
| DESIGN | デザイン | 表層の最終決定 |

> この3役が同一人物の兼務になることは珍しくない。**兼務は「確認を省いてよい」という意味ではない。**
> 詳細は `skills/analyze/uiux/rules/01-layer-discipline.md`。

## 3. 業務用語 — 書き方だけをここに置く

**業務用語の中身は plugin に書かない。** 役割名も主要タスクも業種で変わり、
ここに1つのプロダクトの語彙を置くと、他のプロダクトで間違った言葉を強制することになる。

**定義先: `pd/specs/01-strategy/glossary.md`**（`/pd:init` が雛形を作る）。
以下はその書き方。

### 3.1 利用者の呼称

利用者系統ごとに呼称を1つ決め、**その呼称以外を使わない**。

> ⚠️ **「ユーザー」という語を単独で使わない。** 必ずどの系統かを指定する。
> 系統をまたいだ「ユーザーが不便」は、誰の何が不便なのか分からないまま合意が成立する。

呼称は `pd/voices/taxonomy.json` の `speaker_role` と対応させる（台帳から引けなくなるため）。

### 3.2 主要タスク時間

**利用者系統ごとに1つ定義する。** 系統が2つあれば時間も2つある。
**片方の時間だけを改善して「速くなった」と言わない。**

各時間は**必ず要素に分解して定義する**。全体と部分を混同しないため。

```
<主要タスク時間> = <要素1> + <要素2> + <要素3>
```

⚠️ **部分の改善を全体の改善と呼ばない。**
末尾の1要素だけを縮めて「主要タスクが速くなった」と書くのが最も多い事故。

### 3.3 品質の4軸

時間側とは**必ず対で**扱う。時間だけの改善報告をしない。

| 軸 | 問い |
|---|---|
| 正確さ | 意図した結果に到達したか（誤操作・取り違えが無いか） |
| ダイレクトさ | 目的まで最短で辿り着けたか（迂回・往復が無いか） |
| スピード | 主要タスク時間そのもの |
| ユーザー体験 | 迷い・不安・不快が無かったか |

> 各軸の自社定義（何をどう測るか）は `pd/specs/01-strategy/kpi.md` に書く。**未取得なら「未取得」と書く。**

### 3.4 分類軸を増やしたくなったら

ロケール・プラン・デバイスなど、プロダクト固有の分類軸が要るときは
**ボイスの frontmatter にキーを増やさず** `tags` に `<軸>:<値>` の形で入れる（例: `locale:en`）。
真実の源（その軸の値がどこで決まっているか）を用語集に1行で書き添える。

## 4. 混同されやすい語

| ✕ 混同 | ◯ 区別 |
|---|---|
| 実装済み / 解消 | **実装済み**＝機能の有無。**解消**＝再検証で再発しないと確認した状態 |
| pain / request | **pain**＝困っている事実。**request**＝話者が出した解決手段 |
| コアに据える / 面積を最大化する | コアであることは、画面上で最大であることを意味しない |
| 確認できない / 存在しない | 調査範囲を添えない限り「無い」と書かない |
