# 運用の劣化と対処

**仕組みが死ぬのは、壊れるときではなく使われなくなるとき。**
壊れたら検証器が止める。使われなくなっても、検証器は何も言わない（対象が増えないだけなので通り続ける）。

導入から時間が経つと現れる症状と、その原因・対処を挙げる。
**症状を見たら、人の努力ではなく仕組みを直す。**

---

## 1. スキルが呼ばれなくなった

| | |
|---|---|
| 症状 | UI/UX の話をしているのに層の判定が始まらない。ボイスが記録されない |
| 原因 | `description` のトリガー語が、実際の言い回しと合っていない |
| 対処 | **呼ばれなかった発言をそのまま `description` に足す。** 言い換えを想像で増やさない |

利用者は「使いにくい」とは言わず「なんか違う」「前のほうがよかった」と言う。
実際に出た表現を集める以外に、当てる方法はない。

## 2. 台帳が更新されない

| | |
|---|---|
| 症状 | ボイスの件数が数週間動いていない。一方で「そういえば言われた」という話は出ている |
| 原因 | **記録の手間が、引き当ての利益を上回っている** |
| 対処 | 記録時に埋める項目を減らす。ヒアリング直後にまとめて投入する |

件数0は「問題が無い」ではなく「記録されていない」。
**件数が動かないこと自体を異常として扱う。**

## 3. 決定が記録されない

| | |
|---|---|
| 症状 | 議論の結論は出ているのに `decisions/` が増えない |
| 原因 | 「決めた」瞬間にスキルが呼ばれていない |
| 対処 | 規約側（`CLAUDE.md`）の記述を強める。**決めなかったことも記録対象**だと明示する |

特に落ちやすいのは**決められなかったとき**。
決まらなかった議論は「何も無かったこと」になりやすく、同じ議論が数か月後に再燃する。

## 4. spec が古いまま実装が進む

| | |
|---|---|
| 症状 | 実装と spec の記述が食い違う。誰も spec を読まなくなる |
| 原因 | 上流が変わったときの連鎖（`ux-update-cascade`）が回っていない |
| 対処 | 連鎖のトリガー（新しい利用者層 / 検証結果 / 計測データ / ボイスの傾向変化）をレビューの定例に組み込む |

## 5. 検証が常に赤い

| | |
|---|---|
| 症状 | 違反が出たままコミットが続く |
| 原因 | 「壊れている」と「これから作るもの」を同じ重さで扱っている |
| 対処 | **導入直後が赤くなる設計にしない。** 一度でも「赤くて正常」を作ると、以後の赤は誰にも読まれない |

未着手（Context が空、ボイス0件）は違反ではない。
違反にするのは**書いたものが規約に反しているとき**だけ。

## 6. 規約と検証器がずれる

| | |
|---|---|
| 症状 | 文書どおりに書いたのに検証器が弾く。原因が分かりにくい |
| 原因 | 規約を書いた文書と、判定するコードを片方だけ変えた |
| 対処 | **一致を人の注意力に委ねない。**両者が食い違ったら自己テストで落ちるようにする |

実例: ボイスの `source` の許容値が、スキーマ文書では `operator-validation`、CLI では `user-validation` と
ずれていた。人は文書を見て書き、CLI がそれを弾く。**どちらが正しいのか判断する材料が現場に無い。**

この plugin では `voice-schema.md` / `scripts/voices.mjs` / `scripts/validate.py` の3つが同じ enum を持つ。
食い違いは `scripts/selftest.sh` が検出する（§「スキーマの三者一致」）。
