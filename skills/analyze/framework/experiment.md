# Experiment

原因仮説をどう検証し、次の意思決定につなげるかを定義する。

仮説の因果構造の書き方は `discovery.md` を参照する。ここでは、その仮説の優先順位付けと、検証設計への変換を扱う。

---

## Hypothesis Priority

複数の仮説がある場合、必要に応じて次で優先順位を付ける。

| 観点 | 問い |
|---|---|
| Impact | 正しかった場合、成果への影響はどれだけ大きいか |
| Confidence | 現時点でどれだけ確からしいか |
| Evidence | 支持する Evidence はあるか。その状態は何か |
| Testability | 現実的に検証できるか |
| Effort | 検証と介入にかかる労力はどれだけか |

無理に精密な点数を付ける必要はない。`High` / `Medium` / `Low` で構わない。数値を創作しない。

Impact が大きくても検証できない仮説は、先に**検証可能な形に置き換えられないか**を検討する。

---

## Experiment

改善施策は、確定事項として実装するのではなく、可能な限り Experiment として設計する。

| 項目 | 内容 |
|---|---|
| Hypothesis | 検証する因果の主張 |
| Intervention | 何を変えるか |
| Target | 誰を対象にするか |
| Leading Indicator | 最初に動く signal |
| Outcome KPI | 最終的に意味のある結果 |
| **予測値** | **どれくらい動くと思うか**を実施前に書く（例: 完了率 34% → 40〜45%）。当たり外れを後から測るため |
| Success Criteria | 成功と見なす閾値。**実施前**に決める |
| Required Evidence | そのために必要な計測。存在しないなら先に用意する |
| Duration | 期間。見積もれない場合は `不明` とする |
| Sample | 対象数。見積もれない場合は `不明` とする |
| Decision Rule | 各結果に対して、次に何をするか |

不明な項目を推測で埋めない。特に Duration と Sample は、現状の母数が分からなければ見積もれない。分からないまま数字を置かない。

### 事前に決めること

Success Criteria と Decision Rule は、結果を見る前に決める。結果を見てから成功の定義を決めるのは Experiment ではない。

**予測値も事前に書く。** Success Criteria（合否の線）とは別に、「実際はどこに着地すると思うか」を書く。データが無くても書ける — むしろ Evidence が薄いときこそ、自分の見立てを記録する価値がある。

結果が出たら、予測と実測を `products/{product-name}.md` の Past Experiments に残す。**これを数回積むと、自分たちの見立てがどれだけ当たるかが分かる。** Confidence の `High / Medium / Low` が実測で校正され、以後の判断の重みが変わる。

Decision Rule は、想定される結果それぞれに対応させる。

```
Leading ↑ / Outcome ↑  → 展開する
Leading ↑ / Outcome →  → 連鎖のどこで切れているかを特定する
Leading →              → 介入が Driver に届いていない。Lever の選定に戻る
```

### 検証できない場合

計測が無い、対象が少なすぎる、不可逆である、倫理的制約がある — 検証できない理由を明示したうえで、**代わりに得られる弱い Evidence** を示す。

例: 全数での前後比較、限定した対象での試行、定性観察、類似機能での代理指標。

弱い Evidence であることを、結果の解釈に持ち越す。

## Experiment Result

結果は、事前に決めた Success Criteria に照らして記述する。

- 実際に観測されたこと（`Fact`）
- そこから読み取れること（`Interpretation`）
- 説明できていないこと（`Unknown`）

期待した結果が出なかった場合、それは失敗ではなく、仮説の棄却という結果である。棄却された仮説は記録する。同じ仮説を後で再び持ち出さないため。

想定外の結果が出た場合、事後に説明を作らない。新しい仮説として立て、別に検証する。

## Decision

Evidence をもとに、次の判断を行う。

一般的な形:

```
Continue    現状の方針を維持する
Improve     方向は正しい。介入を改善する
Re-test     結果が判断に足りない。設計を直して再検証する
Scale       効果が確認された。対象を広げる
Stop        効果が無い、または前提が崩れた。中止する
```

導入・公開の判断が必要な場合:

```
GO
CONDITIONAL GO
ITERATE
NO GO
```

対象プロダクトに適した形式を選ぶ。

すべての Decision に、次を添える。

- 根拠となった Evidence と、その状態（`Fact` / `Interpretation`）
- 確からしさ（High / Medium / Low）
- どうなったら見直すか。**誰が・いつ確認するか**まで書く（確認者と時期の無い見直し条件は、実行されない）

導入・継続の判断では、Primary KPI だけでなく**成果指標に載らない価値**（`kpi.md` を参照）とコストを対で示す。価値の列挙で終わらせず、コストと比較した結論を書く。

Decision は `analyses/` の Note に記録し、有効な決定と見直し条件は `products/{product-name}.md` の Decisions へ反映する。Note は履歴、Context は現在値。

`CONDITIONAL GO` は条件を明示する。確認できない条件は、条件ではない。

## 期限のある判断

期限が決まっている判断では、`Re-test` / `ITERATE` は「判断の先送り」として機能しない。期限内に出せる判断を、Evidence の状態を明示したまま作る。

### 手順

```
1. 期限までに変えられないことを先に確定する（対象数・期間・計測の有無）
2. 残り期間で取得できる Evidence を列挙し、判断を分岐させる力の順に並べる
3. 取得しても判断が変わらない Evidence は取りに行かない
4. 取得できないものは Unknown として固定し、その上で判断を書く
```

判断を分岐させる力とは、**その値がどちらに出るかで結論が変わること**。どちらに出ても同じ結論なら、期限内に取る価値は無い。

### 判断の書き方

Evidence が不足したまま判断する場合、次の3つを分けて示す。

| 要素 | 内容 |
|---|---|
| 判断 | 期限時点での結論 |
| 判断の根拠 | 何を Fact として、何を Unknown のまま置いたか |
| 判断が変わる条件 | どの観測が出たら結論を変えるか。誰が・いつ確認するか |

「情報が足りないので判断できない」で終わらせない。不足を明示した判断は、判断として成立する。

### 条件付きの判断

`CONDITIONAL GO` を選ぶ場合、条件を**期間・閾値・観測手段**の3点に落とす。3点が揃わない条件は、実質的な `GO` である。

```
条件      : 何が満たされること
閾値      : どの値を境に満たされたと見なすか
期間      : いつまでに
観測手段  : 何で確認するか（存在しない場合、先に用意する対象になる）
見直し    : 満たされなかった場合に何をするか
```

### 検証期間そのものの再定義

期限内の観測が、介入の効果ではなく **前段の状態**（到達・習熟・運用の定着）を測っていたと判明する場合がある。この場合、期間の結果を「効果の検証結果」として読まない。

```
観測されたもの: 前段が成立していなかったこと
検証されたもの: 介入の効果ではない
```

そのうえで、前段を成立させる条件と、効果検証に必要な観測を分けて次期の設計に渡す。**期間を無駄だったことにしない。** 前段の不成立は、それ自体が Evidence である。

ただし、これを毎回の逃げ道にしない。前段が成立しない理由が介入の設計側にあるなら、それは効果の検証結果として扱う。
