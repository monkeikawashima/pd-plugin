# Discovery

問題をどう理解し、原因まで掘るかを定義する。必要な節だけを読む。

基本の思考構造:

```
Context → Problem → Evidence → Driver → Hypothesis → Experiment → Decision
```

内部の手順として使う。この構造をそのまま毎回ユーザーへ表示しない。

---

## Problem Definition

現象と問題と原因を混同しない。

```
現象:
  利用率が低い

問題:
  対象機能が、ユーザーの実際の業務手順の中に組み込まれていない

原因候補:
  Awareness / Trigger / Learning / Usability / Trust / Value / Workflow
```

指標の変化は現象である。問題の記述には、**どこで・誰に**その損失が起きているかが含まれる。

確認事項:

- 現象を原因として扱っていないか
- どのセグメント・どの工程・どの瞬間に起きているか
- 何と比較しての変化か（前期間 / 他セグメント / 期待値）
- 計測方法や計測対象自体が変わっていないか

原因候補を Evidence なしで確定しない。介入が届きうる範囲まで問題を絞り込んでから次へ進む。

## Evidence

### 4つの状態

| 状態 | 意味 |
|---|---|
| `Fact` | 実際に確認・計測された情報 |
| `Interpretation` | Fact から合理的に読み取れること。別の読み方もありうる |
| `Hypothesis` | まだ検証されていない原因仮説 |
| `Unknown` | 現時点では判断できない情報 |

Interpretation が、後の記述で Fact として引用されることを許さない。

### 3つの種類

**Quantitative** — KPI、Analytics、Usage Logs、Funnel、Conversion、Retention、Task Time、Error、Frequency、Adoption

**Qualitative** — User Interview、ユーザー観察、操作動画、Survey、Support、Sales Feedback、Customer Feedback

**画面** — スクリーンショット、画面録画、実機の操作観察。3種のどれとも違い、**「何ができる状態か」しか示さない**。扱いは後述の「画面から得られる Evidence」を参照

**Behavioral** — 実際のユーザー行動、操作順序、利用頻度、離脱、Retry、回避行動、利用有無

### 品質の確認

- 平均は分布を隠す。セグメント・分位・外れ値を見る
- 少数サンプル・短期間は方向性までしか示さない。そう明記する
- 自己申告された行動は、行動そのものではない
- データが無いことは、事象が無いことの証明ではない
- 計測の実装自体が変更されていないか確認する

## Voice

ユーザーインタビュー・商談・サポート・営業同席などで得た発話。Qualitative Evidence の中核であり、定量では見えない機構を与える唯一の情報源。

### 記録

```
逐語で残す。要約しない。
1件 = 1発話者の1トピック。
```

要約の時点で解釈が混入し、後から別の読み方を試せなくなる。各件に次を添える。

| 項目 | 内容 |
|---|---|
| 発話者 | 誰か（役割・立場・利用状況） |
| 日付 | いつの発話か |
| 文脈 | どの場面での発話か（商談 / 障害後 / 定例 / 観察中 など） |
| 問い | どう聞いたか。誘導があったかどうか |

**問いの立て方が答えを作る。** 「使いにくいですか」への同意は Evidence として弱い。何が起きたかを事実として語らせた部分と、評価・要望を述べた部分を分けて記録する。

### 匿名化

逐語には個人が特定できる情報が入る。記録の時点で落とす。

- 発話者は**役割・立場と ID** で書く。ID の形は **`役割 + 英大文字 + ハイフン + 数字`**（`運用者A-1`（小規模・紙運用が中心）／`利用者B-2`）。実名・組織名・連絡先・アカウント名を書かない
- 敬称の有無は関係ない。**姓だけでも書かない**（「担当の〇〇に確認します」のような発話内の言及も置き換える）
- 発話の中に固有名詞が出た場合、意味が保てる範囲で置き換える（`〇〇社の△△` → `取引先の基幹システム`）
- ID と実名の対応表は、リポジトリの外に置く

分析に必要なのは「誰が言ったか」ではなく「**どの立場の人が言ったか**」である。匿名化で失われる情報は無い。

### ラベル付け

発話そのものと、発話内容の真偽を混同しない。

```
Fact           : その人がそう述べたこと
Interpretation : 述べた内容から読み取れる問題の所在
Hypothesis     : その問題が成果指標に影響しているという主張
```

「使いにくい」という発話から `Usability に問題がある` を導いた時点で Interpretation である。要望をそのまま Solution として採用しない（`Solution Jumping`）。

### 件数と偏り

- **飽和で判断する** — 新しい論点が出なくなるまで集める。固定の目標件数を先に決めない
- 少数の Voice は**論点の発見**には十分だが、**頻度・効果量の推定**には使えない。優先順位を Voice の件数で決めない
- 最も欠けやすいのは、**語ってくれない人の声** — 非利用者、離脱者、解約者、沈黙している多数。集まった Voice は「話す動機のあった人」に偏る。この偏りを結果の解釈に持ち越す
- 自己申告された行動は行動そのものではない（前節「品質の確認」を参照）

### 使いどころ

| 使える | 使えない |
|---|---|
| Hypothesis の生成 | 効果量の推定 |
| Root Cause 候補の発見 | 頻度・分布の推定 |
| 定量で見えた現象の機構の説明 | Driver の優先順位の確定 |
| UX 観点（Awareness / Trigger / …）のどこで失敗しているかの特定 | 施策の効果の証明 |

各 Voice を UX 観点のどれに当たるかで分類すると、定量の分解結果と突き合わせられる。Voice と定量が食い違う場合、どちらかが誤りとは限らない — 対象の Segment が違う可能性を先に確認する。

Voice を1件も持たない状態で Qualitative Evidence を「あり」としない。無ければ `情報不足` と書く。

## 画面から得られる Evidence

スクリーンショット・画面録画・実機の操作観察。**画面は「何ができる状態か」を示すが、「実際にどうされたか」は示さない。** この境界を守る。

### 型と、取れるもの

| 型 | 取れるもの | 取れないもの |
|---|---|---|
| 静止画（スクリーンショット） | 画面の構造・情報量・導線の有無 | 操作の順序、迷い、頻度 |
| 画面録画 | 操作の順序、やり直し、停止した箇所 | 頻度、母集団での分布 |
| 実機の操作観察 | 上記＋発話・つまずきの理由 | 同上。観察者がいる影響も乗る |

いずれも**1件の観測**であり、母集団の性質ではない。

### ラベルの切り分け

同じ画面から3種の記述が出る。混ぜない。

```
Fact           画面上に観測できるもの
               項目数 / 必須項目数 / 文言 / 選択肢の数 / 階層の深さ /
               初期値 / エラー表示の有無 / 確認手順の有無 / 1画面あたりの操作数

Interpretation それをどう読むか
               「選択肢が多く判断しづらい」「次に何をすべきか読み取れない」

Hypothesis     それが成果に影響しているという主張
               「この画面が原因で完了率が下がっている」
```

**「分かりにくい」は `Fact` にならない。** 画面の構造は観測できるが、使う人が迷ったかどうかは画面に映っていない。

`Fact` は**数えられる形**で書く。「項目が多い」ではなく「入力項目9件・うち必須6件」。数えられない記述は Interpretation である。

### 判定できる UX 観点、できない観点

| 画面から判定できる | 画面からは判定できない |
|---|---|
| Learning（手順が読み取れるか） | Awareness（存在を知っているか） |
| Usability（操作が成立するか） | Trigger（使う場面できっかけがあるか） |
| Accuracy（結果が正しく表示されるか） | Adoption（実際に試しているか） |
| Workflow の一部（前後の制約が画面に現れている範囲） | Value（使わない場合より良いか） |

**できない側を、画面を見て埋めない。** Awareness / Trigger / Adoption / Value は、利用データか Voice でしか判定できない。

### 記録の仕方

- **画像を Note に貼らない。** 観測した内容を文章と数値で書く（画像はリポジトリに残さない）
- 出典を添える — **どの画面 / いつ時点 / どの版 / どの条件**（ログイン状態・データ件数・言語など）。画面は変わるため、これが無いと再現できない
- 個人情報が写り込んでいる場合、**転記の時点で落とす**（実名・連絡先・アカウント名・固有名）
- 1画面だけで Journey を語らない。工程をまたぐ話は `User Journey / Task Flow` を使う

### 限界

画面を見ると原因が分かった気になる。**構造の問題を見つけたことは、それが成果を動かしている証明ではない。** 頻度も影響量も画面には無い。

```
画面で分かる  : 何が起こりうるか（原因候補）
分からない    : それが何回起きているか、成果をどれだけ動かしているか
```

そのため、画面から出た論点は**次の突き合わせに渡す**（次節）。画面 → そのまま改善案は `Solution Jumping` である。

## 定量と定性の突き合わせ

片方だけでは原因に届かない。定量は**どこで**が分かるが**なぜ**が分からない。定性は**なぜ**の候補が出るが**どれだけ**が分からない。往復させる。

```
定量で局在させる  →  その Segment / 工程の当事者の Voice を読む  →  機構の仮説
        ↑                                                              ↓
        └────────  その機構が真なら観測されるはずの指標で確認  ────────┘
```

### 画面から始める場合

1. 画面から観測できる `Fact` を数えられる形で書く（前節）
2. そこから出た論点が真なら、**どの指標がどう出るはずか**を書く
3. その指標を確認する。指標が無ければ、不足 Evidence として扱う
4. 可能なら、その工程の当事者の Voice で機構を確かめる

**画面 → 改善案の直行を禁じる。** 構造の問題が見つかったことは、それが成果を動かしている証明ではない。

### Voice から始める場合

1. 発話から論点を抽出する（前節を参照）
2. その論点が真なら、**どの指標がどう出るはずか**を先に書く
3. その指標を確認する。存在しなければ、不足 Evidence として扱う

「Voice で言われていたので対応する」は、頻度も影響も分からないまま優先順位を決めている。

### 定量から始める場合

1. 指標を Segment / 工程まで分解する（`kpi.md`）
2. **その分解結果が指している当事者**の Voice を読む。全体の Voice ではない
3. 数値の動きを説明できる機構が Voice の中にあるかを確認する

説明が見つからない場合、機構を創作しない。`Unknown` として残す。

### 食い違ったとき

| 状況 | 先に確認すること |
|---|---|
| Voice では問題が語られるが、指標に出ない | 母集団が違う（少数の声か、指標が対象外か）／指標がその現象を捉えていない |
| 指標は悪いが、Voice では問題が語られない | 当事者が問題として認識していない／聞き方が届いていない／語れない立場にある |
| Voice と指標が逆を向く | 比較期間・対象範囲の定義が両者でずれている |

**どちらかを誤りと決めない。** 食い違いそのものが、問題の所在を示す Evidence である。

## User Behavior 分析

利用率・定着・離脱の問題で使う。

- **Funnel** — どこで止まるか。初回で止まるか、何度か試した後か
- **順序** — 成功したユーザーがやっていて、失敗したユーザーがやっていないことは何か
- **頻度** — 一度きりか反復か。習慣になっているか
- **回避行動** — 機能を通らずに迂回していないか。別の手段で代替していないか
- **比較** — 利用者 / 非利用者、高頻度 / 低頻度、新規 / 継続

使われていない機能と、使われて失敗している機能は、成果指標の上では同じに見える。診断の前に区別する。

## UX 分析

Evidence と問題に関連する項目だけを使う。全項目を毎回埋めるチェックリストではない。

| 観点 | 答える問い |
|---|---|
| Awareness | その機能の存在を知っているか |
| Trigger | 使うべき場面で、使うきっかけがあるか |
| Adoption | そもそも試しているか |
| Learning | 使い方を理解できるか |
| Usability | エラーなく操作できるか |
| Accuracy | 正しい結果が出るか |
| Trust | その結果を信じて行動できるか |
| Value | 使わない場合より良いか |
| Workflow | 前後の業務・ツール・制約に収まるか |

前段の観点が失敗していると、後段は測定できない。順に診断する。

## User Journey / Task Flow

問題が複数の工程にまたがる場合に使う。

- **User Journey** — きっかけから価値の実感までの全体経路。工程・チャネル・セッションをまたぐ損失を見る
- **Task Flow** — 1つの操作の内部。手順数、入力項目、待ち時間、やり直し、判断の迷いを見る

どちらも、対象プロダクトの実態から作る。一般的な journey の型を当てはめない。

## Root Cause Analysis

候補は Evidence から導く。直感から始めない。問題の形に合う方法を選ぶ。

| 方法 | 適する場面 |
|---|---|
| 5 Whys | 単一の因果連鎖が想定される |
| Funnel Analysis | 段階のある process の中で損失している |
| Journey Analysis | 損失が工程・チャネル・セッションをまたぐ |
| Task Analysis | 1つの操作の内部に問題がある |
| Segmentation | 影響がユーザーによって偏っている |
| Cohort Analysis | 参加時期によって挙動が異なる |
| Before / After | 特定の変更が疑われる |
| User / Non-user | 採用されるかどうかが論点 |
| Heavy / Light User | 価値の実感が論点 |

各候補について、**成立するために何が真である必要があるか**と、**何が観測されたら棄却されるか**を書く。何によっても棄却されない候補は Root Cause ではなく、ただの物語である。

**棄却条件は観測可能な閾値で書く。** 文章で書くと、結果を見てから「これは高いと言えるか」を議論することになる。

```
✅ 棄却条件: 該当操作の完了率 ≧ 70% が実測されたら棄却
❌ 棄却条件: 完了率が高い実測が出れば棄却
```

データが無くて閾値の根拠が薄い場合は、**暫定であることを明示**して数値を置く。数値が無いまま先へ進まない。

フレームワークを使うこと自体を目的にしない。

## Driver

成果に影響している要因を Driver として整理する。必要に応じて次の4軸で評価する。

| 軸 | 問い |
|---|---|
| Impact | それが動いたとき、成果はどれだけ動くか |
| Evidence | 何が支持しているか。その状態は Fact か Interpretation か |
| Confidence | どれだけ確からしいか（High / Medium / Low） |
| Controllability | 実際に変えられるか |

Impact × Confidence × Controllability で並べる。Impact は高いが誰も動かせない Driver は、追う Driver ではなく、設計上の制約として扱う。

最終的に、**最も改善効果が高い可能性のある Driver** を特定する。

KPI から Driver を分解する手順は `kpi.md` を参照する。

## Hypothesis

Root Cause 候補を、因果構造を持つ形に落とす。現象の言い換えは仮説ではない。

```
X が原因で Y が発生し、
その結果 Z へ影響している。
```

または、

```
もし X が原因であれば、
X を変化させることで Y が変化するはずである。
```

すべての仮説に、**それが棄却される観測**を添える。閾値の書き方は `Root Cause Analysis` と同じ（観測可能な数値で書く。暫定なら明示する）。

## 反証

分析の最後に、**自分の結論を最も強く否定する Evidence** を書く。棄却条件が個々の候補を対象にするのに対し、これは**結論全体**を対象にする。

```
何が観測されたら、この結論は誤りだったと言えるか
それを取りに行くコストはどれくらいか
```

箇条書き2〜3行で足りる。長く書くと形骸化する。

**目的は確証バイアスの検出。** 支持する方向にだけ Evidence を並べていないかを、書き手自身に点検させる。ここで「否定する観測が思いつかない」なら、それは結論が強いのではなく**反証不可能な主張になっている**（`framework/discovery.md` の Root Cause の原則と同じ）。

複数の仮説の優先順位付けと、検証設計への変換は `experiment.md` を参照する。

## Improvement Lever

Driver と Solution を区別する。

```
悪い例:
  チュートリアル動画を作る    ← これは Solution。機構を決める前に手段が出ている

良い例:
  Driver           : 利用開始後の離脱
  Improvement Lever: Learning
  Intervention     : チュートリアル動画 / 初回ガイド / 既定値の変更 …
```

構造:

```
Driver → Improvement Lever → Intervention
```

代表的な Lever: Awareness、Trigger、Adoption、Learning、Usability、Accuracy、Trust、Value、Task Time、Error Rate、Workflow Fit

各 Lever について、**どの Driver をどういう機構で動かすか**と、**その Driver が効くと言える Evidence** を示す。施策そのものを Driver として扱わない。
