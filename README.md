# pd

数字と利用者の声から原因を突き止め、UI/UX の改善まで進めるための **Claude Code 拡張機能（プラグイン）** です。

調査・意思決定・UI/UX 改善・効果検証まで、同じ場所で一貫して進められます。

分析の専門知識は要りません。日本語で質問するだけです。

## 使い方

**必要なもの**: Claude Code と Python 3（`python3 --version` で確認）。macOS / Linux / Windows で動きます。

```
/plugin marketplace add monkeikawashima/pd-plugin
/plugin install pd@pd-plugin     ← 入れる（1回だけ）
/pd:init                         ← 使うプロジェクトで準備（プロジェクトごとに1回）
```

あとは質問するだけです。

```
/pd:analyze 〇〇                                     ← 対象のプロダクト名だけ
/pd:analyze 〇〇 の利用率が低い理由を知りたい             ← プロダクト名 + 知りたいこと
/pd:analyze 機能を作ったのに使われていない。原因を知りたい  ← 文章だけでも動きます
```

**聞き方のコツ** — 原因を推測して伝えると、その推測に引っ張られた答えが返ります。**困っている状態をそのまま**書いてください。

```
△  UI が分かりにくいので改善案を出して      → 「UI が原因」を前提にしてしまう
◎  作ったのに使われていない。原因を知りたい   → 知らない / 使えない / 価値が無い に分けて調べる
```

`/pd:init` は置き場所とチェックを用意します。**既にあるファイルは触りません。**

**データを先に準備する必要はありません** — 会話に数字を書く、`@` でファイルを指定する、DB から取ってもらう、どれでも構いません。**まだ何も計測していなくても始められます**（「そもそも測る仕組みが無い」も結論のひとつです）。

### Notion などのリンクを渡す

Notion が Claude Code に接続されていれば（MCP 連携）、**URL を貼るだけで中身を読み取って材料にします。** 要件定義・議事録・インタビュー記録・Support ログなど、コピーして貼り直す必要はありません。

```
/pd:analyze 〇〇 の利用率が低い理由を知りたい
最新の要件定義はこれです https://www.notion.so/...
```

**「いつのものか」を伝える必要はありません。** ページの更新日を自動で読み取り、古い資料か最新かを判断します。判断した結果は分析の中に出るので、間違っていればその場で直せます。

```
参照した外部ソース
  ✓ 〇〇 要件定義        更新 2026-07-28  → 最新として扱う
  ⚠ 〇〇 キックオフ議事録  更新 2025-11-02  → 古い資料として扱う
  ? 〇〇 共有メモ         更新日 取得できず  → 数字の根拠には使わない
```

更新日が取れなかったときだけ「いつのものですか」と聞かれます。

**次に活かすかどうかは、その場で聞かれます。** リンクから読んだ内容で「前提（KPI の現在値など）」が変わる場合、分析の最後に**変更点の一覧と「反映する／選んで反映する／しない」**が出ます。こちらから「反映して」と頼む必要はありません。

反映しなかった項目も、その回の分析結果には残ります。**次回の前提として引き継がれないだけ**です。上書きになる項目は変更前の値も一緒に出るので、見てから決められます。

## 何ができるか

**調べるだけの道具ではありません。** まだ無いものを作るときにも、既にあるものを直すときにも使えます。

| 段階 | できること |
|---|---|
| **探索** | 何を聞くか決める／インタビューと行動観察を計画する（「聞かないこと」を先に決めます） |
| **記録** | 利用者の声を、要約せず言葉のまま貯める |
| **戦略** | 声を数え上げて利用者像（ペルソナ）を作る／誰のために・何を成功と呼ぶかを言葉にする |
| **分析** | 数字を分解して、変化が起きている場所と原因を絞る |
| **要件** | 利用者の流れ（ジャーニー）を手が止まる単位に区切る／ユーザーストーリーに落とす |
| **構造** | 画面に置く「もの」を決める／どこから辿り着けるか（導線・メニュー）を確定させる |
| **画面** | 実装の前に画面仕様を書く（「結果が0件だった」「エラーになった」を含む5つの状態も一緒に） |
| **見た目** | 文言を点検する／色のコントラストとキーボード操作を検算する／トークンを台帳で管理する |
| **評価** | 実装した UI を、その画面に届いた声に照らしてレビューする |
| **検証** | 決まらない論点を検証計画にする／効果を数値で測る |
| **決定** | 決めたこと・決めなかったことを残す／前提が変わったら下流に「要再検証」を付ける |

**どの段階の話かは、先に切り分けます。** 「使いにくい」と言われたときに、色の話なのか要件の話なのかを確かめてから進みます（取り違えると、色を変えるべきでないときに色を変えることになります）。

**材料が足りなくても止まりません。** 分からないことは「何が分かれば決まるか・誰が・いつまでに」の形で残り、分かった時点で続きから進められます。

## 何が起きるか

### 思いつきで原因を決めません

1. **見つける** — データを分解して、変化が起きている場所を特定する
2. **確かめる** — 利用者の声から、その理由を裏づける
3. **決める** — 根拠をもとに改善案を選ぶ
4. **測る** — 何が起きたら成功・失敗と言えるかを先に決め、あとで確かめる

### 結論だけでなく、判断の過程が残ります

| 残るもの | 中身 |
|---|---|
| **根拠** | その結論に至った理由。確認できた事実か、推測かの印つき |
| **決められなかったこと** | 何が分かれば決まるか ／ いつまでに ／ 誰が |
| **見直しの条件** | 何が起きたら、この判断を考え直すか |

利用者の声は、**要約せず実際の言葉のまま**蓄積します。
画面を改善するときは、**その画面に関する声を先に確認してから**変更します。

## 元データの置き場所だけ注意

`/pd:init` は `pd/.local/` を作ります。CSV・録音・スクショなどの元データを一時的に置く場所で、共有されない設定も一緒に入ります。作業が終わったら中身を消してください。

⚠️ **ただし「共有されない」保証はありません。** このフォルダごとクラウドストレージで同期していると、中の個人情報も一緒に渡ります。**同期から除外する**か、**プロジェクトの外に置く**（例: `~/pd-data/`）かを必ず行ってください。

実名や CSV がうっかり混ざった場合は、書いた時点で自動的に指摘されます。

## UI/UX を直す

**思いつきで直さず、誰が何に困ったかから始めます。** 声は逐語のまま記録され、画面を直すときは**その画面の声を先に引き当てます**。

> **0件 = 問題が無い、ではありません。記録されていないだけです。**
> 0件でも改善案は出せますが「**デザイナー起案**」と明記されます。お客様の要望だったことにしないためです。

戸惑いやすい挙動を挙げます。**どれも仕様どおりです。**

| 話題 | 起きること |
|---|---|
| **「使いにくい」** | まず「どの段階の話か」を聞かれます（方針〜見た目の5段階）。取り違えると、色を変えるべきでないときに色を変えます |
| **色** | 最終決定しません。基準を割っていれば、色みを保って明るさだけ動かした**下限値**を出します。決めるのはあなたです |
| **ペルソナ** | 創作しません。声を役割ごとに数え上げます。0件の役割は「未取得」。年齢・性別などの属性も持たせません |
| **ジャーニー** | 手が止まる単位に区切り、その区切りがそのまま測り方になります。測っていない区間は「未取得」。**末尾だけ速くして「速くなった」とは言いません** |
| **画面仕様** | 作る前に書きます。「0件だったとき」「エラーのとき」を必ず含めます |
| **課題が未定** | インタビューの前に「**聞かないこと**」を決めます（「あったら使いますか」は全員が「使う」と答えます）。終わりは人数ではなく「新しい話が出なくなったら」 |
| **キーボード操作** | マウス前提のまま出さないよう点検します。確かめられなかった項目は「未確認」 |
| **メニューに足す** | そのままは通りません。何の入口か・どこから辿り着けるかを先に決めます |
| **声が無い画面** | 13の観点で走査し、直す順番まで出します。ただし**「専門家がそう見た」だけ**と明記され、声があればそちらが優先です |
| **競合** | 「**相場**（無いと落ちる）」と「**差別化**（あるから選ばれる）」に仕分けます。**2社以上が持てば相場**。「競合にあるから作る」は通りません |
| **Figma** | 仕様と突き合わせ、色・余白・画面の抜けを一覧に。**どちらを正とするか決めるまで書き込みません** |

そして次の6つでは、**作業を止めて聞き返します。**

- 設計図の合意
- 画面に置く「もの」の確定（開発チームの同席が必要）
- 色の最終決定
- 検証の人数・時期・実施者
- 逐語が無い声の深刻度
- 甲乙つけがたい案の選択（両方並べて、何を測れば決まるかまで出します）

### モックは、リンクで返ってきます

「モックを作って」「画面案がほしい」と頼むと、**公開されたページ（Artifact）として作られ、URL が返ります。**
手元のフォルダに HTML が置かれて終わり、にはなりません。

以前は、同じ頼み方をしてもリンクで返るときとファイルで終わるときがありました。
**利用者から見ると、何が条件なのか分かりません。** ここを固定しています。

| | |
|---|---|
| **効く範囲** | plugin を入れた**全プロジェクト**。`/pd:init` していなくても効きます |
| **邪魔にならないか** | モック・画面案・ワイヤー・プロトタイプ等の語に当たったときだけ動きます。無関係な会話では黙ります |
| **止めたいとき** | 「ローカルだけに作って」「公開しないで」と添えてください。促されません |
| **作り直すとき** | 同じ URL に上書きされます。リンクを貼り直す必要はありません |
| **公開範囲** | 既定は**非公開**です。共有するかは、できあがってからあなたが決めます |

書いたのに公開せずに終わろうとした場合は、**一度だけ差し戻されます。** 公開できない環境ではその理由が1行返り、そこで終わります。

なお「API のモック」「テストダブル」を頼んだ場合は対象外です。

## どこに何ができるか

`/pd:init` が作るものは、すべて `pd/` の中に収まります。**やめるときに、どれが pd のものか分かるようにするためです。**

| 場所 | 中身 | 書き換え |
|---|---|---|
| `pd/products/` | 今の状況メモ | ✅ 最新に上書きしていく |
| `pd/specs/` | 画面や方針の現在値 | ✅ 最新に上書きしていく |
| `pd/analyses/` | 分析の結果 | ❌ 過去は直さず、書き足す |
| `pd/voices/` | 話した言葉、そのまま | ❌ 要約に書き換えない |
| `pd/decisions/` | 決めたこと・決めなかったこと | ❌ 過去は直さず、書き足す |
| `pd/.local/` | 元データの一時置き場 | ✅ 消えてよい・共有しない |

ほかに `validations/`（検証の計画）`measurements/`（計測の計画）`reviews/`（画面レビュー）`simulations/`（予測。**根拠には使いません**）と、`ledger.json`（書き換えの検出用。触りません）ができます。

`pd/` の外に出るのは `CLAUDE.md` と `.github/workflows/` の2つだけです。

### 言葉は自分で決めます

pd は業種の言葉を持ちません。「利用者」を何と呼ぶかは、プロダクトごとに違うためです。

| 場所 | 決めるもの |
|---|---|
| `pd/specs/01-strategy/glossary.md` | 利用者の呼称・主要タスク時間・業務用語 |
| `pd/voices/taxonomy.json` | 話した人の役割・対象物・場面 |

どちらも**空**で作られます。**「未定義」のままで構いません**（埋めないと止まる、ということはありません）。役割を書き込むと、**その時点からそこに無い言葉が弾かれます**（`店舗スタッフ` と `Staff` が混ざると、後から声を引けなくなるためです）。

## 出てきたファイルの読み方

> **「たぶんこうだろう」と「確かにこうだった」を、絶対に混ぜない。**

これが pd の根っこです。すべての記述に印がつきます。

| 印 | 意味 | 例（SaaS） | 例（申込型サービス） |
|---|---|---|---|
| `Fact` | 実際に確認できた | 「その機能を使ったのは全体の12%だった」 | 「申込は月30件だった」 |
| `Interpretation` | そこから読み取れること | 「そもそも気づかれていないのかも」 | 「知られていないからかも」 |
| `Hypothesis` | まだ確かめていない考え | 「導線を増やせば使われるはず」 | 「告知を増やせば増えるはず」 |
| `Unknown` | 分からない | 「どのプランの利用者かは不明」 | 「どこから来た利用者かは不明」 |

**用語を覚える必要はありません。** 見出しには「`Evidence（根拠）`」のように日本語が併記され、冒頭に凡例が入ります。**迷ったら下から読んでください** — 「Decision（判断）」と「不足情報」だけで、何をすればいいかは分かります。

**よくあるのは、式に分解すると前提が崩れるパターンです。**

```
最初の見立て   「利用が増えれば売上が増える」
分解すると     売上 = 利用件数 × 課金対象になる割合  ← ここを誰も見ていなかった
分かること     課金対象にならない経路が多いと、利用が増えても売上は増えない
次にやること   その割合を1度だけ集計する（多くはクエリ1本）
```

次にやることが「大きな改善策」ではなく「1本の集計」になります。

## 過去の記録は上書きできません

`pd/products/` と `pd/specs/`（どちらも「今の状態」を持つ場所）**以外は、すべて書き足すだけ**の場所です。分析・声・決定・検証計画・計測計画・レビュー結果が含まれます。過去のファイルを変更すると検証が止まります。

見出しの言い換えを足したなど**表記だけの修正**なら `/pd:validate --accept` で承認でき、承認した事実も記録に残ります。**判断・数値・結論を変えたいときは承認せず**、新しいファイルに「前回との違い」を書きます。

⚠️ この仕組みは**変更を知らせるだけで、元に戻せません。** バックアップは別途用意してください。

## 更新する

```
/pd:update
```

これ1つで済みます。終わったら `/reload-plugins`（今のセッションに反映）。**分析データは消えません**（入れ替わるのは plugin 側だけ。変更点は [CHANGELOG.md](CHANGELOG.md)）。

**新しい版が出ると、起動時にお知らせが出ます。**（`/pd:init` 済みのプロジェクトのみ。オフラインでは出ませんが作業は妨げません）

⚠️ **`/plugin update pd@pd-plugin` だけでは更新されません。** 手元の配布元一覧しか見ないため、新しい版に気づけず、**古い版へ戻すこともあります。** `/pd:update` は「一覧の取り直し → 更新」をこの順で行います（手打ちなら `/plugin marketplace update pd-plugin` → `/plugin update pd@pd-plugin`）。

**放っておくと届きません。** Claude Code は公式以外の配布元を既定で自動更新しません。常に最新でよければ `/plugin` → Marketplaces → pd-plugin → **Enable auto-update**。ただし**チームでは手動を勧めます**（チェックのルールが勝手に変わると、昨日まで通っていたファイルが今日落ちるため）。

**確認そのものを止めるには** `PD_UPDATE_CHECK=0`。起動のたびに版番号を読むだけで、あなたのファイルは何も送りません → [SECURITY.md](SECURITY.md)。

## やめる

```
/pd:uninstall                    何があるかを一覧表示するだけ（何も消しません）
/pd:uninstall --keep-data        仕組みだけ消す。分析結果は残す
/pd:uninstall --purge            分析結果ごと全部消す
/plugin uninstall pd@pd-plugin   plugin 本体を外す
```

**先に `/pd:uninstall` を実行してください。** plugin を外すとこのコマンドも一緒に消え、後から片付けられません。

⚠️ **消した記録は戻りません。** 共有していれば履歴には残りますが、手元のファイルは復元されません。`--purge` の前に、消える件数を必ず確認してください。
