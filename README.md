# pd

**「たぶんこれが原因だと思う」を、「これが根拠です」に変える Claude Code の拡張機能です。**

数字が悪いとき、原因を思いつきで決めずにデータと利用者の声から順にたどります。結論だけでなく、**何を根拠にそう考えたか**と、**何が起きたら考えを変えるか**まで残ります。

**v2.0.0 から、UI/UX の改善も同じ場所で回せます。**利用者の声を逐語で溜め、画面を直す前にその画面の声を引き当て、決めたこと・決めなかったことを残すまでが入っています。別の道具を足す必要はありません。

分析の専門知識は要りません。日本語で質問するだけです。
**向いていないこと**: コードを書く、進捗報告を作る。

```
とにかく使ってみたい      →  「使ってみる」だけで始められます
何を渡せばいいか不安       →  「データの渡し方」
UI・デザインを直したい     →  「UI/UX の改善」
どこに何が増えるのか       →  「フォルダの意味」
出てきたファイルを読む     →  「分析結果の読み方」
やめたくなった            →  「やめる」
```

## 使ってみる

**必要なもの**: Claude Code と **Python 3**（`python3 --version` で確認）。macOS / Linux / Windows で動きます。ほかに入れるものはありません。

**1. 入れる**（1回だけ）

```
/plugin marketplace add monkeikawashima/pd-plugin
/plugin install pd@pd-plugin
```

**2. 使うプロジェクトで準備する**（プロジェクトごとに1回だけ）

```
/pd:pd-init
```

置き場所・台帳・チェックが用意されます。既にあるファイルは触りません。

コマンドが `/pd:` で始まるのは、Claude Code が plugin ごとに名前空間を付けるためです。先頭の数文字を打てば候補に出ます。

**3. 更新の受け取り方を決める**（1回だけ）

**更新は放っておくと届きません。** Claude Code は公式以外の配布元を既定で自動更新しないためです。

| | やり方 | 向いている場合 |
|---|---|---|
| **手動**（既定） | 下の「更新する」を必要なとき実行 | チームで使う。判定が勝手に変わると困る |
| **自動** | `/plugin` → Marketplaces → pd-plugin → **Enable auto-update** | ひとりで使う。常に最新でよい |

**4. 質問する**

```
/pd:pd 〇〇                                     ← 対象の名前だけ
/pd:pd 〇〇 の利用率が低い理由を知りたい            ← 名前 + 知りたいこと
/pd:pd 機能を作ったのに使われていない。原因を知りたい  ← 文章だけでも動きます
```

保存先とファイル名は pd 側が判断します。短い質問には短く返ります。

**聞き方のコツ** — 困っている状態をそのまま書きます。原因を推測して伝えると、その推測に引っ張られた答えが返ります。

```
△  UI が分かりにくいので改善案を出して      → 「UI が原因」を前提にしてしまう
◎  作ったのに使われていない。原因を知りたい   → 知らない / 使えない / 価値が無い に分けて調べる
```

## データの渡し方

**先に完璧に準備する必要はありません。** 楽な方法から。

```
① 会話に書く          先月の申込は120件、完了は34件でした      ← 整形不要。これで十分
② ファイルを指定       @export.csv どこで止まっているか分析して
③ DB から取ってもらう   申込テーブルから月別の件数を集計して
④ 手元で実行して渡す    ! を先頭に付けるとコマンドの結果が会話に入る
```

使う材料は4種類です。**数字**（DB・解析ツール・管理画面）／**声**（インタビュー・商談・問い合わせ）／**行動**（利用ログ・イベント計測）／**画面**（スクショ・録画・横で見る）。

**画面には限界があります。** 分かるのは「何が表示されているか」まで。「誰がどこで詰まったか、何回起きたか」は分かりません。だから画面だけでは原因になりません。**原因の候補**までで、頻度と影響は数字か声で確かめます。残すのは画像ではなく、数えられる形にした事実です。

```
❌ 「入力フォームが分かりにくい」         ← 感想（読み取り）
✅ 「入力項目9件・うち必須6件・確認画面なし」 ← 事実
```

**データが無い / 取れないときは、そのまま伝えてください。** 「計測していない」「権限がない」も分析結果になります。**何が足りないか / なぜ必要か / どう取れるか / 取れたら何が決まるか**の形で残り、次にやることが決まります。いちばん重要な結論が「そもそも測る仕組みが無い」になることは珍しくありません。

## 元データの扱い（重要）

**元データそのもの（CSV・エクスポート・画面の写真）は共有されるファイルとして残しません。**

```
✅ 集計した結果の数字        例: 先月の完了は34件
✅ その数字を取ったやり方     クエリ = データを取り出す命令文
❌ CSV や DB の中身をそのまま写したもの
```

個人情報が混ざるリスクを避けるためと、**取り出し方さえ残れば数字はいつでも取り直せる**ためです。

一時的に手元へ置くなら `/pd:pd-init` が作る `pd/.local/〇〇/` に、日付つきの名前で。共有されない設定（`.gitignore`）も一緒に入ります。**中でさらにフォルダを分けないでください** — 整えるほど「保管庫」に見え、消されなくなります。作業が終わったら中身を削除します。

⚠️ **`pd/.local/` が「共有されない」保証はありません。** このフォルダごとクラウドストレージで同期していると、中の個人情報も一緒に渡ります。**A. 同期設定で `pd/.local/` を除外する** か **B. 一時データをプロジェクトの外に置く**（例: `~/pd-data/〇〇/`）のどちらかを必ず行ってください。

**お客様の声に名前を書きません。** 必要なのはどの立場の人が言ったかで、誰が言ったかではありません。録音・文字起こし・名前の対応表も `pd/.local/` かプロジェクトの外へ。

```
❌ 「A社の〇〇さんが『前のやり方のほうが早い』と言っていた」
✅ 「利用者A-1（小規模・導入3ヶ月）: 『前のやり方のほうが早い』」
```

## UI/UX の改善

画面やデザインを直すときも、同じ考え方で進めます。**思いつきで直さず、誰が何に困ったかから始めます。**

やることは3つだけです。

**1. 声を溜める。**「お客さんがこう言っていた」と伝えるだけで、逐語のまま記録されます。要約しません。言い換えると、後から「本当は何と言ったのか」が分からなくなるためです。

**2. 直す前に引き当てる。**「この画面を直したい」と言うと、その画面について記録された声を先に出します。

```
0件 = 問題が無い、ではありません。記録されていないだけです。
```

声が0件のまま改善案を出すこともできますが、その場合は**「デザイナー起案」と明記されます**。お客様の要望だったことにしないためです。

**3. 決めたことを残す。**「これで進めます」と言うと記録されます。**決められなかったことも残します。**「何が分かれば決まるか」「いつまでに」「誰が」の3つが埋まらないものは、未決定として認められません。「保留」とだけ書いて終わらせないためです。

### 迷ったら層を聞かれます

「使いにくい」という一言でも、原因は**方針**（そもそも誰向けか）から**見た目**（文字が小さい）まで5段階のどこかにあります。層を取り違えると、色を変えるべきでないときに色を変えることになります。最初に層を判定してから進みます。

### 色に触るとき

「この色にしたい」と言うと、コントラスト比を計算します。**目分量で置きません。**基準を満たさない場合は、色みを保ったまま明るさだけ動かした**下限値**を出します。

最終的にどの色にするかはデザイナーが決めます。plugin が出すのは「ここまでは必要」という線だけです。

### 止まるところ

次の6つでは、勝手に決めずに聞きます。

- 設計図の合意（人が決めること）
- 画面に置く「もの」の確定（開発チームの同席が必要）
- 色の最終決定（デザイナーの領域）
- 検証の人数・時期・実施者（段取りは人が決める）
- 逐語が無い声の深刻度（判断材料が足りない）
- 甲乙つけがたい案の選択（両方並べて、何を測れば決まるかまで出します）

## フォルダの意味

`/pd:pd-init` でプロジェクト側に用意されるものと、その扱い方です。**pd が作るものは `pd/` の中にまとまります。**

| 場所 | 中身 | たとえるなら | 書き換えていい？ |
|---|---|---|---|
| `pd/products/〇〇.md` | 今の状況メモ | **メモ** | ✅ 最新に上書きしていく |
| `pd/analyses/〇〇/2026/` | 分析の結果 | **日記** | ❌ 過去は直さず、書き足す |
| `pd/voices/〇〇/2026/` | 話した言葉、そのまま | **録音** | ❌ 要約に書き換えない |
| `pd/simulations/〇〇/2026/` | 予測。本物ではない | **練習用のダミー** | ⚠️ 根拠として使わない |
| `pd/specs/` | 画面や方針の現在値 | **設計図** | ✅ 最新に上書きしていく |
| `pd/decisions/〇〇/2026/` | 決めたこと・決めなかったこと | **議事録** | ❌ 過去は直さず、書き足す |
| `pd/validations/〇〇/2026/` | 検証の計画 | **実験ノート** | ❌ 同上 |
| `pd/measurements/〇〇/2026/` | 計測の計画 | **物差しの定義** | ❌ 同上 |
| `pd/reviews/〇〇/2026/` | 画面レビューの結果 | **指摘メモ** | ❌ 同上 |
| `pd/.local/〇〇/` | 元データの一時置き場 | **作業机の上** | ✅ 消えてよい・共有しない |
| `pd/ledger.json` | 書き換えを検出する台帳 | — | 触りません |

**1つのフォルダに集めているのは、やめるときのためです。** プロジェクトの直下に `products/` `analyses/` が散っていると、名前だけでは pd のものか判別できません。

ほかに `CLAUDE.md`（このプロジェクトのルール）と、GitHub を使っていれば `.github/workflows/`（共有時に同じチェックを走らせる設定）ができます。この2つだけが `pd/` の外に出ます。

**v1.4.0 より前から使っている場合**、これらはプロジェクトの直下にあります。**そのままで動きます**（移動は不要です）。整理したい場合は「置き場所を移す」を参照してください。

**分析の「やり方」はここにありません。** plugin 側にあり `/plugin update` で新しくなります。だからプロジェクト側は更新で消えません。やり方を変えたくなったら、それは**共通のやり方に個別事情が混ざっている**か**状況メモの項目が足りない**かのどちらかなので、メモのほうを見直します。

ファイル名は日付と主題だけ。**中身の説明を名前に入れません。**

```
pd/analyses/〇〇/2026/20260812-01-kpi.md      ← 8月12日の1件目、主題は KPI
pd/analyses/〇〇/2026/20260812-02-voice.md    ← 同じ日の2件目、主題はお客様の声
```

## いちばん大事な考え方

> **「たぶんこうだろう」と「確かにこうだった」を、絶対に混ぜない。**

すべての文に印をつけます。後から読んだ人が事実と推測を見分けられるようにするためです。**推測を事実として引用しない** — これが崩れると分析全体が信用できなくなります。

| 印 | 意味 | 例 |
|---|---|---|
| `Fact` | 実際に確認できた | 「申込は月30件だった」 |
| `Interpretation` | そこから読み取れること | 「申込が少ないのは知られていないからかも」 |
| `Hypothesis` | まだ確かめていない考え | 「告知を増やせば申込も増えるはず」 |
| `Unknown` | 分からない | 「どこから来た利用者かは不明」 |

声がまだ1件も無いなら「無い」と書きます。予測で埋めません（`pd/simulations/` は、その予測を本物と間違えないよう隔離する場所です）。

## 分析結果の読み方

**用語を覚える必要はありません。** 見出しには「`Evidence（根拠）`」「`Root Cause（根っこの原因）`」のように日本語が併記され、冒頭に印の凡例が入ります。**ファイル単体で読めるようにしてあります。**

迷ったら**下から読んでください** — 「Decision（判断）」と「不足情報（次に調べること）」だけで、何をすればいいかは分かります。

**よくあるのは、式に分解すると前提が崩れるパターンです。**

```
最初の見立て   「利用が増えれば売上が増える」
分解すると     売上 = 利用件数 × 課金対象になる割合  ← ここを誰も見ていなかった
分かること     課金対象にならない経路が多いと、利用が増えても売上は増えない
次にやること   その割合を1度だけ集計する（多くはクエリ1本）
```

構造を分解すると、次にやることが「大きな改善策」ではなく「1本の集計」になります。

## 間違いは自動で見つかります

ルールを暗記する必要はありません。外れたものは機械が指摘します。

```
作業開始 → 残っている問題を通知      書いた直後 → その場で指摘（直してから進む）
作業終了 → 残っている問題を通知      共有時    → 同じチェックが自動で走る（GitHub の場合）
```

**見ているもの**: 置き場所と名前 / 必須の項目 / **お客様の実名が残っていないか** / 元データが混ざっていないか / 過去の記録が書き換わっていないか。自分で確認したいときは `/pd:pd-validate`。

`pd/analyses/` と `pd/voices/` は書き足すだけの場所なので、過去のファイルを変更すると止まります。見出しの言い換えを足したなど**表記だけの変更**なら `/pd:pd-validate --accept` で承認でき、承認した事実は記録に残ります。**判断・数値・結論を変えたい場合は承認しないでください** — 新しいファイルに「前回との違い」を書きます。

⚠️ この仕組みは**変更を知らせるだけで、元に戻せません。** バックアップは別途用意してください。

**チームで使うときは、あと2つ。** 分析結果と状況メモは**まとめて一緒に共有**します（別々だと、どの分析がメモを変えたのか追えません）。そして**一覧ファイル（`pd/analyses/index.md` のようなもの）を作りません** — 年フォルダを開けばファイル名が一覧で、別に作ると必ず更新漏れが起きます。「今どれが未決か」は状況メモの**「保留中の見直し」**だけが管理台帳です。

## 更新する

```
/plugin marketplace update pd-plugin     配布元の一覧を取り直す
/plugin update pd@pd-plugin              plugin 本体を更新する
/reload-plugins                          今のセッションに反映する
```

**分析データは消えません。** 入れ替わるのは plugin 側だけです。**何が変わるかは [CHANGELOG.md](CHANGELOG.md) にあります** — チェックのルールが変わった版では、今まで通っていたファイルが指摘されることがあります。

## やめる

**プロジェクトから片付ける**

```
/pd:pd-uninstall                何があるかを一覧表示するだけ（何も消しません）
/pd:pd-uninstall --keep-data    仕組みだけ消す。分析結果は残す
/pd:pd-uninstall --purge        分析結果ごと全部消す
```

**先にこれを実行してください。** plugin を外すと `/pd:pd-uninstall` も一緒に消え、後から実行できません。

**plugin 本体を外す**

```
/plugin uninstall pd@pd-plugin
```

これはプロジェクト側のファイルには触りません。**だから片付けは上のコマンドが必要です。**

⚠️ **消した記録は戻りません。** 共有していれば履歴には残りますが、手元のファイルは復元されません。`--purge` の前に、消える件数を必ず確認してください。

## 置き場所を移す

v1.4.0 より前から使っている場合、フォルダはプロジェクトの直下にあります。**そのままで動きます。** 移したいときだけ、次の順で。

```
1. 共有できていない変更が無いことを確認する（移動の途中で失敗しても戻せるように）
2. products / analyses / voices / simulations を pd/ の中へ移す
3. .gitignore の .local/ を pd/.local/ に直す
4. /pd:pd-validate
```

**台帳は作り直す必要がありません。** 記録の場所は `pd/` から見た位置で覚えているため、まとめて移しても同じものだと分かります。4 で違反が出なければ完了です。
