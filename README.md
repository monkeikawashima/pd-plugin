# pd

**「たぶんこれが原因だと思う」を、「これが根拠です」に変える Claude Code の拡張機能です。**

プロダクトの数字が悪いとき、原因を思いつきで決めずに、データと利用者の声から順番にたどります。結論だけでなく、**何を根拠にそう考えたか**と、**何が起きたら考えを変えるか**まで文章で残ります。

---

## 誰のためのもの

| こんな人 | pd がやること |
|---|---|
| 数字が落ちた理由を聞かれて困っている | 原因の候補を分解して、確からしい順に並べる |
| 改善案は出るが、根拠が弱いと言われる | どの数字・どの声が根拠かを対応づけて書く |
| 分析するたびに前回の話が消える | 1回=1ファイルで残り、過去は書き換わらない |
| チームで判断がブレる | 「確認済み」と「まだ推測」を全文で区別する |

分析の専門知識は要りません。日本語で質問するだけです。

**向いていないこと**: コードを書く、UI 仕様を決める、進捗報告を作る。

### どこから読めばいいか

```
とにかく使ってみたい      →  「使ってみる」だけで始められます
何を渡せばいいか不安       →  「分析に使うデータをどう用意するか」
どこに何が増えるのか       →  「フォルダの意味」
出てきたファイルを読む     →  「分析結果の読み方」
```

上から順に読む必要はありません。

## 使ってみる

**1. 入れる**（1回だけ）

```
/plugin marketplace add monkeikawashima/pd-plugin
/plugin install pd@pd-plugin
```

**2. 使うプロジェクトで準備する**（プロジェクトごとに1回だけ）

```
/pd-init
```

置き場所・台帳・チェックの仕組みが用意されます（詳細は「フォルダの意味」）。既にあるファイルは触りません。

**3. 更新の受け取り方を決める**（1回だけ）

**更新は放っておくと届きません。** Claude Code は、公式以外の配布元を既定で自動更新しないためです。次のどちらかを選んでください。

| | やり方 | 向いている場合 |
|---|---|---|
| **手動**（既定） | 下の「更新する」を必要なときに実行 | チームで使う。判定ルールが勝手に変わると困る |
| **自動** | `/plugin` → Marketplaces → pd-plugin → **Enable auto-update** | ひとりで使う。常に最新でよい |

自動にすると、セッション開始から10分以内に更新され、更新された旨が通知されます。

**4. 質問する**

```
/pd 〇〇                                     ← 対象の名前だけ
/pd 〇〇 の利用率が低い理由を知りたい            ← 名前 + 知りたいこと
/pd 機能を作ったのに使われていない。原因を知りたい  ← 文章だけでも動きます
```

書き方は自由です。**どのファイルに何という名前で保存するかは、pd 側が判断します。**

### 聞き方のコツ

**困っている状態をそのまま書くのが、いちばん良い聞き方です。** 原因を推測して伝えると、その推測に引っ張られた答えが返ってきます。

```
△  UI が分かりにくいので改善案を出して
      → 「UI が原因」という前提を確定させてしまう

◎  機能を作ったのに使われていない。原因を知りたい
      → 使われない理由を、知らない / 使えない / 価値が無い などに分けて調べる
```

短い質問には短く返ってきます。毎回すべての項目が埋まったレポートが出るわけではありません。

## 分析に使うデータをどう用意するか

ここがいちばん詰まりやすいところです。**先に完璧に準備する必要はありません。**

### 4種類あります

| 種類 | 何か | どこから取るか |
|---|---|---|
| **数字** | 何人が使ったか、何件申し込まれたか | データベース、アクセス解析、決済や社内の管理画面、表計算 |
| **声** | お客様が実際に言ったこと | インタビュー、商談、問い合わせ、営業からの共有 |
| **行動** | どこで止まったか、何回使ったか | 利用ログ、イベント計測ツール |
| **画面** | 今どういう画面になっているか | スクリーンショット、画面録画、操作を横で見る |

### 渡し方（楽なものから）

**① 数字を会話に書く**

```
先月の申込は 120件、そのうち完了は 34件でした
```

これで十分です。整形も不要です。

**② ファイルを置いて場所を伝える**

```
@export.csv このデータで、どこで止まっているか分析して
```

**③ データベースから直接取ってもらう**

```
申込テーブルから、月別の件数を集計して
```

**④ 自分でコマンドを実行して結果を渡す**

入力欄の先頭に `!` を付けると、その場でコマンドが動いて、結果が会話に入ります。

### 画面（スクショ）を渡すときの注意

画面から分かることには**はっきりした限界**があります。

```
分かる     : 何が表示されているか（項目数・文言・導線の有無・階層の深さ）
分からない : 実際に誰がどこで詰まったか、それが何回起きているか
```

画面だけでは「これが原因」になりません。**原因の候補**までです。頻度と影響は数字か声で確かめます。残るのは画像ではなく、数えられる形にした事実です。

```
❌ 「入力フォームが分かりにくい」         ← これは感想（読み取り）
✅ 「入力項目9件・うち必須6件・確認画面なし」 ← これが事実
```

### データが無い / 取れないとき

そのまま伝えてください。「計測していない」「本番を見る権限がない」も分析結果になります。**何が足りないか / なぜ必要か / どう取れるか / 取れたら何が決まるか**の形で残るので、次にやることが決まります。いちばん重要な結論が「そもそも測る仕組みが無い」になることは珍しくありません。

## 元データの扱い（重要）

**元データそのもの（CSV・エクスポート・画面の写真）は、共有されるファイルとしては残しません。**

```
✅ 集計した結果の数字（例: 先月の完了は34件）
✅ その数字を取ったやり方（クエリ = データを取り出すための命令文）
❌ CSV やデータベースの中身をそのまま写したもの
```

理由は2つ。個人情報が混ざるリスクと、**取り出し方さえ残っていれば数字はいつでも取り直せる**ことです。

### 一時的に手元へ置きたいとき

`/pd-init` が作る `.local/〇〇/` に、日付つきのファイル名で置きます。共有されない設定（`.gitignore`）も一緒に入ります。

```
.local/〇〇/20260812-reservations.csv
```

中でさらにフォルダを分けないでください。年別・用途別に整えるほど「保管庫」に見え、消されなくなります。**作業が終わったら中身を削除します。**

⚠️ **`.local/` の中身が「共有されない」保証はありません。** このフォルダごとクラウドストレージや共有ドライブで同期している場合、`.local/` の中の個人情報も一緒に渡ります。どちらかを必ず行ってください。

```
A. 同期サービスの設定で .local/ を除外する
B. 一時データをプロジェクトの外に置く（例: ~/pd-data/〇〇/）  ← 安全
```

### お客様の声には名前を書きません

```
❌ 「A社の担当の〇〇さんが『前のやり方のほうが早い』と言っていた」
✅ 「利用者A-1（小規模・導入3ヶ月）: 『前のやり方のほうが早い』」
```

必要なのは**どの立場の人が言ったか**で、誰が言ったかではありません。名前を落としても情報は失われません。録音・文字起こし・名前の対応表も `.local/` かプロジェクトの外へ。

## フォルダの意味

`/pd-init` を実行すると、プロジェクト側にこれが用意されます。

```
📁 products/〇〇.md            各プロダクトの「今の状況メモ」
📁 analyses/〇〇/2026/         分析の結果。プロダクト別・年別にたまります
📁 voices/〇〇/2026/           お客様が話した言葉、そのまま
📁 simulations/〇〇/2026/      予測。本物ではありません
📁 .local/〇〇/                元データの一時置き場（共有しない）
📁 pd/ledger.json             過去の記録の書き換えを検出する台帳
📄 .github/workflows/         共有したときに同じチェックを走らせる設定
📄 CLAUDE.md                  このプロジェクトのルール（Claude が自動で読みます）
```

**分析の「やり方」はここにありません。** plugin 側にあり、`/plugin update` で新しくなります。だからプロジェクト側のファイルは更新で消えません。

役割が違うので、混ぜないことだけ守ってください。

| 場所 | たとえるなら | 書き換えていい？ |
|---|---|---|
| `analyses/` | **日記** | ❌ 過去の分は直さない。新しく書き足す |
| `voices/` | **録音** | ❌ 要約に書き換えない。言われたまま残す |
| `simulations/` | **練習用のダミー** | ⚠️ 根拠として使わない |
| `products/〇〇.md` | **今の状況メモ** | ✅ 最新に上書きしていく |
| `.local/` | **作業机の上** | ✅ 自由。ただし消えてよい・共有しない |

ファイル名は日付と主題だけの短い形です。**中身の説明を名前に入れません。**

```
analyses/〇〇/2026/20260812-01-kpi.md      ← 8月12日の1件目、主題は KPI
analyses/〇〇/2026/20260812-02-voice.md    ← 同じ日の2件目、主題はお客様の声
```

## いちばん大事な考え方

ルールはぜんぶ、次の一言から来ています。

> **「たぶんこうだろう」と「確かにこうだった」を、絶対に混ぜない。**

なので、すべての文に印をつけます。

| 印 | 意味 | 例 |
|---|---|---|
| `Fact` | 実際に確認できた | 「申込は月30件だった」 |
| `Interpretation` | そこから読み取れること | 「申込が少ないのは知られていないからかもしれない」 |
| `Hypothesis` | まだ確かめていない考え | 「告知を増やせば申込も増えるはず」 |
| `Unknown` | 分からない | 「どこから来た利用者かは不明」 |

この印があるので、後から読んだ人が事実と推測を見分けられます。**推測を事実として引用しない** — これが崩れると、分析全体が信用できなくなります。

## 分析結果の読み方

**分析ファイル自体に説明が入っています。** 見出しには「`Evidence（根拠）`」のように日本語が併記され、冒頭に印の凡例があります。このページを開かなくても読めます。

以下は一覧で見たいとき用です。

| 言葉 | 意味 | ふつうの言い方 |
|---|---|---|
| 現状 | 今どうなっているか | 事実の整理 |
| 問題 | 何が困っているか | 「どこで・誰に」損が出ているか |
| Evidence | 根拠 | 何を見てそう言えるのか |
| Driver | 成果を動かしている要因 | 「ここが動けば結果が変わる」もの |
| Root Cause | 根っこの原因 | 表面の症状ではなく、その大元 |
| Hypothesis | 仮説 | まだ確かめていない「たぶんこう」 |
| Improvement Lever | 改善の効きどころ | どこを押せばいいか（施策そのものではない） |
| Experiment | 検証 | 本当にそうか確かめる方法 |
| Decision | 判断 | 続ける / 直す / やめる |
| 反証 | この結論が崩れる条件 | 何が出てきたら考えを変えるか |
| 不足情報 | 足りない情報 | 次に何を調べるべきか |

読む順番に迷ったら、**下から読んでください。** 「Decision（判断）」と「不足情報（次にやること）」だけ読めば、何をすればいいかは分かります。

## 実際にどう役立つのか

よくあるのは、**式に分解すると前提が崩れる**というパターンです。

```
最初の見立て:  「利用が増えれば売上が増える」

分解すると:    売上 = 利用件数 × 課金対象になる割合
                                  ↑ ここを誰も見ていなかった

分かること:    課金対象にならない経路が多いと、
              利用が増えても売上は増えない

次にやること:  その割合を1度だけ集計する（多くの場合クエリ1本）
```

数字を眺めるだけでは出てこない話です。**構造を分解すると、確かめるべきことが1つに絞れます。** そして次にやることが「大きな改善策」ではなく「1本の集計」になります。

## 間違いは自動で見つかります

ルールを暗記する必要はありません。外れたものは機械が指摘します。

```
作業開始 → 残っている問題を通知
書いた直後 → その場で指摘（直してから進む）
作業終了 → 残っている問題を通知
共有時   → 同じチェックが自動で走る
```

自分で確認したいときは `/pd-validate`。

**見ているもの**: 置き場所と名前 / 必須の項目 / **お客様の実名が残っていないか** / 元データが混ざっていないか / 過去の記録が書き換わっていないか。

### 過去の記録を直したいとき

`analyses/` と `voices/` は**書き足すだけ**の場所です。過去のファイルを変更するとチェックで止まります。

見出しの言い換えを足したなど、**表記だけの変更**なら承認できます。

```
/pd-validate --accept
```

承認した事実は記録に残ります。**判断・数値・結論を変えたい場合は承認しないでください。** 新しいファイルに「前回との違い」を書きます。

⚠️ この仕組みは**変更を知らせるだけで、元に戻せません。** バックアップは別途用意してください。

## チームで使うときの約束

1. **分析1回につきファイル1つ。** 種類ごとに分けない
2. **分析結果と「今の状況メモ」は、まとめて一緒に共有する。** 別々だと、どの分析がメモを変えたのか後から追えません
3. **過去の分析は直さない。** 考えが変わったら新しいファイルに「前回との違い」を書く
4. **一覧ファイル（`analyses/index.md` のようなもの）を作らない**

4つ目について: 一覧が欲しくなるのは自然ですが、**年フォルダを開けばファイル名（日付つき）が一覧です。** 別に作ると必ず更新漏れが起きます。「今どれが未決なのか」は、そのプロダクトの**「今の状況メモ」の「保留中の見直し」**だけを見てください。そこが唯一の管理台帳です。

## 更新する

```
/plugin marketplace update pd-plugin     配布元の一覧を取り直す
/plugin update pd@pd-plugin              plugin 本体を更新する
/reload-plugins                          今のセッションに反映する
```

**分析データは消えません。** 更新で入れ替わるのは plugin 側（分析の進め方・チェックの仕組み）だけです。

**更新すると何が変わるかは [CHANGELOG.md](CHANGELOG.md) にあります。** チェックのルールが変わった版では、今まで通っていたファイルが指摘されることがあります。

## よくある質問

**Q. 何かを壊しそうで怖いです**

`analyses/` と `voices/` は追加していくだけなので、既存のものは壊れません。うっかり過去のファイルを書き換えた場合も、チェックが知らせます。迷ったら `/pd 〇〇を分析したい` と伝えれば、置き場所も命名も pd 側が判断します。

**Q. お客様の声がまだ1件もありません**

「無い」と書きます。予測で埋めません。`simulations/` は、その予測を本物と間違えないように隔離しておく場所です。

**Q. 分析の「やり方」を自分好みに変えたい**

`framework/` は共通なので触りません。変えたくなったら、それは**共通のやり方に個別事情が混ざっている**か、**「今の状況メモ」の項目が足りない**かのどちらかです。メモのほうを見直してください。
